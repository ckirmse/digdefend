Overview


* The apocalypse has arrived and the world’s most valuable resource is Uranium 
* Apocalyptic Mining Co has decided to send its crews to remote and dangerous mining locations to extract Uranium
* For each run, a group of 1-6 players are dropped off at one of these remote mining camps
* Every mining camp has a mine, a processing machine, a segmented wall, 6 mannable posts, a gate, a mining supplies building, a defense building, and a helicopter landing pad.
* The team’s ultimate goal is to collect x amount of Uranium, hidden ever deeper in the mine
* The challenge is that every night a wave of enemies descends on the camp, bent on destroying it, with each wave getting progressively harder
* Players must use the ores and materials they find mining to build and upgrade their camp defenses to keep the enemy hordes at bay at night, so they can mine in the day
* To win, players will need to extract the required amount of Uranium and survive long enough to be airlifted out by the company’s rescue helicopter
* Players lose by dying or having their processing machine destroyed
* In addition to in run currency, players receive Diamonds for reaching certain milestones during each run, which they can use outside the run to unlock new weapons, post upgrades, and defensive placements
* Decided 2026-10-15 (replacing the Characters design of 2026-10-05 and the Class system of 2026-10-03): the lobby economy is Classes (a fixed kit: a handheld weapon, a Post Weapon of its own, a Tower, a Gadget of its own, a buff, a debuff, and three skill slots; twelve designed for launch, how they are unlocked and progressed to be decided once the cost of making one is known), Boosts (per-run consumables, dropped or bought by name), and Contracts (an account-wide ladder of harder tiers per map, each with its own Diamonds reward and a modifier that favours a class, and a weekly contract), which together are the reason to keep playing after a map is beaten. Classes carry the entry purchase, Boosts the recurring spend, Contracts the retention; nothing sold is permanent power. See "Classes", "Boosts", "Monetization", "Earning Diamonds", and "Contracts" near the end of this document
* As players level up their skills, they’ll be able to embark on more challenging missions in different locations 
Place Structure
* The game will have two separate places: a lobby place and a gameplay place. 
* Everyone will join the lobby when they launch the game (start place). This is where players group up, buy upgrades/unlocks/consumables/classes and check event status. 
* The gameplay server is where gameplay takes place and can only be reached via teleports from the lobby
* Players form parties at helicopter pads inside the lobby, which teleport them as a group to a fresh gameplay server where they will play the main game
* Only players in a specific queue should be able to access the specific gameplay server they’re teleported to. Friends and other players should not be able to join an existing gameplay server.

Helicopter Pads – Party Creation/Teleports
* Helicopter Pads teleport parties of players to a new, private instance of the gameplay place
* All 6 pads are identical. A pad is not tied to a map or difficulty. The first player onto an idle pad becomes the party host and configures the run (map, difficulty, party size, visibility). This is modelled on Dead Rails' Create Party flow, without join-by-code. Adding a map or difficulty later means adding it to the party config, not building a pad.
* Every Helicopter Pad has a Helicopter sitting on it when the server initializes (cloned from ReplicatedStorage.GameAssets.Helicopter onto HelicopterSpawn). Its rotor spins (client-side) from Create until the pad returns to Idle. The Helicopter sound rides on every helicopter as a 3D emitter and each client plays it from the first turn of the rotor until the blades are still again or the model is destroyed (decided 2026-09-16), so the sound and the blades always agree.
* Every Helicopter Pad has a billboard gui at its entrance with three labels (decided 2026-09-11):
   * Status: Idle "WAITING FOR PLAYERS...", Boarding "<MAP> (<DIFFICULTY>)" (since 2026-10-09; "Starts in: X" before, the countdown left the billboard that day), Departing "DEPARTING". While Configuring none of the three labels shows: a fourth label, Configuring, fills the panel alone in red with "<DISPLAYNAME> IS SETTING UP A RUN" (designed on Pad1, 2026-10-09). Every label is ALL CAPS
   * Private: hidden while Idle or Configuring; once a party exists it shows "PUBLIC" in green or "PRIVATE" in red from the party config (2026-10-09; muted and gold before). Players reads waiting/max
   * Players: always shows current players / party size (an idle pad reads 0 / MaxPartySize)
* Pad states. Each pad is in exactly one state, held in server Lua and replicated to clients as an attribute on the pad model so the billboard and menus can render it:
   * Idle: empty, no host. Touching the helicopter makes you the host and moves the pad to Configuring.
   * Configuring: the host is on the Create Party Menu. Nobody else can join; touching gives the feedback "Pad is being set up".
   * Boarding: configured and accepting players who pass the join checks.
   * Departing: teleport in progress. Nobody can join; touching gives "Pad is departing".
   * Transitions: Idle → (touch) → Configuring → (Create) → Boarding → (launch) → Departing → (reset) → Idle. Configuring returns to Idle on creation timeout or if the host leaves. Boarding returns to Idle if nobody is left.
* Becoming host
   * A player touches the helicopter on an Idle pad. The server rejects them with "You're already in a party" if they are in a party on any pad.
   * The server sets the pad to Configuring with this player as host and starts the CreationTimer at CreationTimeout.
   * The host's character is seated in the helicopter at the first PlayerSpawn and their camera is moved to CameraPositionPart. While in a party, jumping is disabled so the seat can only be left through the menu (Exit or Cancel); the pad billboards are hidden while a party menu is open.
   * The host's client opens the Create Party Menu.
   * If two players touch an Idle pad at the same time, the first processed becomes host and the second gets "Pad is being set up". Never two hosts.
* Configuring
   * The Create Party Menu shows a countdown. Changing a setting does not reset it: CreationTimeout is a hard limit on how long a pad can be held without committing.
   * If the countdown reaches zero, the host presses Cancel, or the host leaves the game: the host is moved to ExitSpawn, camera returned, menu closed, and the pad returns to Idle. The timeout gives the feedback "Party creation timed out"; Cancel and leaving give none.
   * When the host presses Create, the server validates the selection (see Create validation). If invalid, it rejects with feedback and the pad stays Configuring. If valid, the server records map, difficulty, max players, and visibility on the pad, sets Boarding, stops the CreationTimer, and starts the BoardingTimer at BoardingTimeout. The host's client swaps the Create Party Menu for the Queue Menu in host mode and the billboard shows the configuration.
* Boarding
   * Other players touch the helicopter. The server runs the join checks. On pass, the character is seated at the next free PlayerSpawn, the camera moved, the player added to the party, the count updated on the billboard, and the Queue Menu opened in member mode.
   * When the party reaches max players, the BoardingTimer is set to CapacityTime (a short auto-launch countdown).
   * Leaving: the Exit button in the Queue Menu, or disconnecting (a character that leaves its seat for any other reason, such as dying, also counts as leaving). The character goes to ExitSpawn and the party and billboard update. If a full party drops below full, the timer does not go back up; it keeps counting from where it is (a full party that loses someone in the last two seconds still launches).
   * If the host leaves during Boarding and other players remain, the earliest-joined remaining player becomes host, their Queue Menu switches to host mode, and they get the feedback "You are now the party host". If nobody remains, the pad returns to Idle.
* Launching. Any of these launches:
   * The host presses Launch in the Queue Menu
   * The BoardingTimer reaches zero
   * The CapacityTime countdown reaches zero after the party filled
   * A party of one launches solo. This is allowed and expected.
* On launch:
   * The pad is set to Departing and the billboard shows "Departing". Every client (party or not) sees the helicopter take off: it climbs 100 studs, then flies 1000 studs straight ahead, then disappears; a fresh helicopter is already on the pad by then. For party members the Queue Menu fades out while the camera stays on CameraPositionPart, and 2 seconds later the Departure Loading Screen comes in over the takeoff.
   * Party members' characters are moved to random spawns inside HoldingArea.Spawns. This removes their avatars from view in case of teleport issues.
   * All party members are teleported together (one TeleportAsync call with the player list, never per player) to a fresh reserved gameplay server. Join data: map, difficulty, playerCount (the number actually teleported, not max players; the gameplay server scales from this and never waits for more), hostUserId, padIndex for logging, and memberUserIds. Only players in that party can enter that gameplay server: the reserved server keeps outsiders out, and the gameplay server's arrival gate kicks anyone whose join data is missing or does not list them.
   * A failed teleport is retried (3 attempts, 2 s apart); on final failure the player respawns in SpawnZone with a "Teleport failed" message and their camera and menus are restored. A player who disconnects during Departing is simply excluded from the teleport. A player still in the lobby 10 s after a successful teleport call is treated as a failed teleport.
   * A fresh helicopter model is cloned from ReplicatedStorage, placed at HelicopterSpawn, and parented to the pad model. The pad is cleared and returns to Idle.
* Create validation (server, when the host presses Create). Reject with feedback if any fail:
   * The map and difficulty exist in the party config
   * The host has completed the map's requirement (if any)
   * The host has completed the difficulty's requirement on the selected map (if any)
   * 1 <= max players <= MaxPartySize
   * Visibility is Public or Friends Only
   * The pad is still Configuring and this player is still its host
   * The client greys out locked options, but the server is authoritative. Never trust the client's claim that something is unlocked.
* Join checks (server, on a helicopter touch during Boarding). Reject with the given feedback if any fail:
   * Pad is Boarding: "Pad is being set up" / "Pad is departing"
   * Party has room: "Party is full"
   * Player not already in a party: "You're already in a party"
   * If Friends Only, the joiner is a friend of the host: "This party is friends only"
   * Joiners are not checked against map or difficulty unlocks. Access follows the host: a player who hasn't unlocked Frostbite Pass can join a Frostbite Pass party.
* Progression on completion (gameplay server): a run's completion of (map, difficulty) is recorded for a player only if that player had already completed its prerequisite themselves. A player carried through Nightmare by a friend does not unlock Nightmare. The gameplay server enforces this with the same requirement table the lobby uses.
* Every Helicopter Pad will be a Model, located inside Workspace.HelicopterPads, with a PadIndex attribute (1–6). Inside each model will be:
   * HelicopterModel
      * In the HelicopterModel will be a PlayerSpawns folder of invisible Seat instances (Seat1–Seat6) that party members are seated in. The seats are kept Disabled so the engine never auto-seats a passer-by; the server enables a seat only for its own Sit call and disables it again once it empties.
      * A Rotar model with a Rotar hub part; the blades are welded to the hub and the client spins it about world up.
   * HelicopterSpawn: An invisible part used to place newly spawned HelicopterModels
   * CameraPositionPart: Invisible part that will be used to position the player's camera
   * GuiPart.PadGui: GuiPart is an invisible part that PadGui (BillboardGui) will be parented to. PadGui will display all the necessary info.
   * The helicopter is the join trigger (designer, 2026-10-14): touching any part of the pad's helicopter starts or joins its party; the invisible JoinCollision part that did this before is no longer read and may be removed from the pad models
   * ExitSpawn: an invisible part outside the helicopter pad, where players leaving the party will be moved to
   * Other decorations (not needed by code)
   * Runtime pad state (state, host, map, difficulty, max players, visibility, current player count, departure time) is server Lua replicated as attributes on the pad model. The party member list itself stays on the server; only the count replicates. The pad model carries no authored map, difficulty, or max players values.
* Party config (one GameData module, nothing hardcoded in pad scripts). I need to be able to easily change:
   * CreationTimeout (default 30 s): how long a host has to press Create
   * BoardingTimeout (default 20 s): seconds after Create before auto-launch
   * CapacityTime (default 3 s): countdown once the party is full
   * MaxPartySize (default 6): upper bound on the players stepper
   * DefaultMaxPlayers (default 4) and DefaultVisibility (default Public): the menu's starting values
   * Maps, in carousel order, each with a display name, thumbnail, and an optional requirement (a map/difficulty completion). At launch: Deadman's Canyon (always available), Frostbite Pass (requires Deadman's Canyon on Normal).
   * Difficulties, in carousel order, each with an optional requirement evaluated against the currently selected map. At launch: Normal (always), Hard (requires Normal), Nightmare (requires Hard).
   * The config is validated at server start (unique ids, requirements reference real maps and difficulties, timeouts positive, defaults in range), failing loudly with the offending key named.

Player Feedback Text
* This will be a simple ScreenGui containing a frame called FeedbackBox, with a TextLabel child. 
* There should be a remote event in ReplicatedStorage.Events called “GivePlayerFeedback” and a bindable event called “GivePlayerFeebackLocal”
* The server can fire the remote event (or the client can call the bindable event) with the below variables
   * Player
   * Message
   * TimeDisplay
* The PlayerFeedback gui listens for the events, takes the message, puts in TextLabel.Text, enables the gui, waits the TimeDisplay amount, and then disables the gui. As built (2026-10-05, M32, replacing the three boxes of 2026-09-16 and 2026-09-25): one box, low on the screen just above the tool bar, whose colour says how much a message matters: its own dark colour for ordinary feedback, blue for announcements (a new tier, the rescue's lines, the day starting over), red for alerts (a wall down, the Refinery under attack, "[DisplayName] has died"). A message that matters more is never wiped by a lesser one while it is still showing. A dead player sees no messages at all on the Game Over screen or the Results Menu; they return in Spectate Mode and on revive

Gameplay
Gameplay Overview
* All gameplay in the gameplay server is in first person (lobby is default third person). Admin dev tools free the mouse while a dev window is open.
* The core game consists of repeating the same core loop until the required uranium has been mined or until all players are dead or the mine grinder is destroyed 
* During the day (320 seconds), players harvest resources, upgrade abilities, and place defenses
* Players earn resources by mining raw ore and bringing it to the refinery to be refined into currency (Iron Bars, Gold Bars, and Uranium)
* The deeper players get into the mine, the harder the rock becomes and the more valuable the ore becomes
* After being refined, players can spend their currency on upgrading their mining abilities, upgrading their defense posts, buying/placing defenses, or repairing existing damage
* Gold is used on personal items/upgrades and Iron is used on shared resources. There is no in-run collective currency since 2026-10-06 (M33): Crystal, the in-run Diamond, and the Camp Level were removed in full (see Camp Level)
* Nothing in the stores is gated: every upgrade is a plain Gold or Iron buy, and the mine itself is never locked; depth is gated by rock hardness alone (decided 2026-09-15)
* At night, waves of enemies spawn outside the camp, bent on destruction 
* Players must use their weapons, posts, and defenses to kill the horde before the horde destroys the refinery or kills all the players
* Waves get progressively harder every night, forcing players to think through their defenses and decide whether its better to improve mining speed or defense strength
* Waves spawn over 90 seconds whenever a day ends and lasts until all enemies have been killed, at which point a new day begins
* To win, players must collect the specified amount of Uranium they’ll be able to call the Apocalyptic Mining Co. rescue helicopter
* The monsters will give one final, climatic wave as the rescue helicopter arrives.
* Once safely inside the helicopter, the player has “won”. Maps
* The goal is to continue adding new maps, with fresh layouts, different challenges, new enemies, and obstacles
* At launch the goal is to have 2 different maps
   * Deadman’s Canyon: A desert mine in an old west canyon. This is the starter map, with a base only exposed on one side (so enemies only come from one direction). 
   * Frostbite Pass: An arctic mining facility with brutal weather, more exposure, and more intense enemies
* Each map will have its own separate mine spawn and enemy waves data, so they can be balanced differently. 
Map authoring (decided 2026-09-12)
* All maps live in the one gameplay place. Each map is a Folder under ServerStorage/Maps named by its Enums.Map key (DEADMANS_CANYON, FROSTBITE_PASS). Folders, not Models, so clicking a part in the Explorer selects only that part; things that should move as one unit (the helicopter pad) stay Models inside the folder.
* At run start the server clones the chosen map folder into Workspace as Camp. Only the active map exists in memory. Its scenery is static geometry and is the one place server-side parts are the right call.
* Every map folder carries the same required named parts, validated at startup with the map’s name in every message: HelicopterPad (with HelicopterSpawn and Spawns 1–6), Mine.Entrance (an anchored part whose position is the mine origin and whose look direction is the mine facing, snapped to the nearest axis), Refinery (a Model; refining is automatic within a radius of it since 2026-10-01, so no prompt part), Walls (Wall1 to Wall6) and Posts (Post1 to Post6) folders of numbered Models plus a Gate Model (the fortification markers), MiningStore with its Stands folder, DefenseStore with its Tables folder (TowerTable, PostUpgradeTable with a DisplayPost model, WeaponUpgradeTable, WallsTable with a Gui part and a WallModel; the Workbench by the gate is gone since 2026-10-01), and the monster areas (WaveAreas, CampArea, MonsterSpawns, each with at least one part; an empty WaveAreas left every monster standing still on 2026-10-01). Every Model in the camp outside the Environment folder is set to persistent streaming when the map loads (MapManager, 2026-10-02), so the stores, Refinery, Radio, pad, walls, gate, and posts reach every client on arrival and never stream out; the scenery alone streams by distance. Each MonsterSpawn is checked against the path grid at run start (outside the areas, on blocked ground, or with no route to the Refinery) and named in the Output (2026-10-02).
* Editing a map: run scripts/studio/map_tools.luau in Edit mode with ACTION = "load" to move the map folder into Workspace, edit, then run it with ACTION = "save" to move it back. Pressing Play with a map folder still in Workspace uses it as-is with a warning, so an unsaved edit still plays and is never lost. With the map loaded, ACTION = "preview_mine" generates its mine from Mine.Entrance exactly as the server would and draws translucent labelled boxes (bedrock envelope, the entrance tunnel, each zone, each hand-placed rock) into Workspace/MinePreview so the camp can be built around the real footprint; rerun it after moving the entrance, ACTION = "clear_preview" removes it, "save" removes it, and the server deletes any copy left behind at run start so it never shows in Play.
* Terrain is optional per map. A map that wants terrain adds a TerrainBounds part sized around it; “save” snapshots the terrain inside the bounds into a TerrainRegion in the map folder and “load” pastes it back. A map without TerrainBounds is a plain folder and the tools skip terrain. Terrain lives in the place file only.
* What a map cannot change: rock definitions, the weight kernel, block size, difficulty and party scaling, and the generator. Balance stays comparable between maps.
* A new map is: one Enums.Map entry with a public name, one row in the pad’s map carousel (thumbnail and unlock requirement), one mine file in GameData/Mines plus its registry entry, one wave file in GameData/Waves, and one folder under ServerStorage/Maps.
* Studio has no teleport data, so a dev tool starts a run as any map and difficulty without leaving Play.
Difficulty
* Every map will also have 3 difficulty levels: Normal, Hard, and Nightmare
* Difficulty is driven by the enemy waves. Harder rock is more swings per block, which is grind, not challenge; waves are decisions, positioning, and spending. Levers:
   * Enemy wave composition and count (the main lever): each map has its own generator parameters per difficulty, so a harder difficulty starts higher, climbs faster, and brings the strong kinds on earlier nights; a monster’s HP and damage never change with difficulty (decided 2026-09-24)
   * Ore scarcity: fewer veins on Hard and Nightmare, so upgrade choices bite (see Randomized Mine Creation §7). Uranium has its own, steeper divisor (URANIUM_VEIN_DIVISOR, 1.0 / 1.1 / 1.15; decided 2026-09-28), so a harder run finds it slower too
   * Rock hardness never changes with difficulty by default (the knob exists but is off); mine layout never changes with difficulty or player count
* Every number above is checked by the balance sheet (decided 2026-09-28, docs/balance-plan.md): BalanceModel (shared, pure) plays a run on paper from GameData, day by day (swings, backpack trips that lengthen with the tunnel, Gold split across the upgrade ladders, Iron into the best towers) and night by night (the generator's budget as HP against the crew's posts and towers, the leak that survives the walk beating on the wall, the final wave), and BalanceAudit runs it for every audited map and difficulty at crews of 1, 4, and 6 at gameplay startup, warning per missed target. The targets live in GameData/Control/Balance: 10 / 12 / 14 nights per difficulty, 20 Gold by the end of night 1, a wall dented then nearly broken then broken on Normal's nights 2 to 4 (Hard and Nightmare breach on night 2), and each tier above the easier one through that one's target night. Its guesses about play (ASSUMPTIONS) were fitted to the fifth playtest's log; the Monsters dev panel prints the sheet
Party scaling
* Parties are 1 to 6 players and the count can drop mid-run. The mine grid is fixed at generation and never resized; everything that scales with party size is applied at the moment of effect (a rock breaking, a wave spawning) from the current player count, so drop-outs adjust the run with nothing to migrate.
* Levers live in one PartyScaling table keyed by player count 1–6 (GameData/Control/PartyScaling), so 3 players can be tuned separately from 5:
   * Wave difficulty and enemy HP multipliers (WAVE_DIFFICULTY_MULTIPLIER_BY_PLAYER_COUNT, ENEMY_HP_MULTIPLIER_BY_PLAYER_COUNT). The main lever: a bigger crew digs faster and attracts bigger nights. As built (M30): the generator aims for the night’s difficulty times the wave multiplier (an authored wave has every count multiplied instead, rounded half up), and every monster spawns with its HP times the HP multiplier; both read the crew count sampled at dawn, and the day-start line ends “Waves 1.60x”. The wave multiplier was matched to the uranium table on 2026-09-25 (1.0, 1.5, 2.0, 2.5, 3.0, 3.5), and the map’s MIN_GROUP_DIFFICULTY is multiplied by it too, so a bigger crew meets the same number of groups as a solo player, each that much bigger. As of 2026-09-28 the HP multiplier is 1 at every crew size (a crew scales the night through the budget only, so the two never compound; four players had met 3.25x solo HP) and the wave table is sublinear, 1.0 / 1.6 / 2.1 / 2.4 / 2.6 / 2.8: the camp's tower cap is shared, so a big crew's towers plateau where a solo player's do
   * Uranium rescue target multiplier, near-linear (1.0, 1.5, 2.0, 2.5, 3.0, 3.5 from solo to six; steepened from 1.0 to 1.25 on 2026-09-25: a crew digs about as many times faster as it is large, so the modest table let six players finish before the nights escalated while a solo run had to survive night 8 and beyond). Every mine must author enough uranium for the largest party; the generator validates supply against target × the six-player multiplier. The difficulty multiplies the target too (GameData/Control/Difficulty URANIUM_TARGET_MULTIPLIER: Normal 1.0, Hard 1.15, Nightmare 1.3; M31), and the generator checks the mine’s supply against the worst case of both, so Deadman’s Canyon authors 135 uranium for a solo target of 30 (6 / 9 / 9 / 111: 20%, 30%, 30% of the solo target in the first three zones, the rest in zone 4; decided 2026-09-25 after a 50 minute solo playtest at 2 / 4 / 8 / 20 against 20 found none, the target raised from 25 the same day). A scaled target is rounded to the nearest 5, halves up (RefineryRules.URANIUM_TARGET_STEP, decided 2026-09-25), so the radio reads 40 for two players rather than 38, and the generator rounds its worst-case check the same way As of 2026-09-28 the table is 1.0 / 2.5 / 4.5 / 8 / 10 / 12 (the balance sheet has a crew stripping every zone it passes and hunting the hum), the difficulty multipliers are 1.0 / 1.2 / 1.7, the solo target is 35 (2026-10-23; 40 before), and Deadman's Canyon authors 9 / 14 / 20 / 950 (the fifth playtest found 40 by day 4 at 26 / 40 / 56; zone 4 covers 40 x 1.7 x 12 = 816 against the thinned 863). Since 2026-10-26 the supply is counted in ore and Deadman’s Canyon authors 7 / 8 / 9 Uranium 1 in zones 1 to 3, 8 Uranium 2 (24 ore) in zone 4, and 60 Uranium 3 (360 ore) in zone 5: 35 x 1.7 x 5.0 = 300 for six on Nightmare against the thinned 354
   * Per-player ore yield multiplier, applied only to Iron and Gold drops because those balances are per player. Diamonds and Uranium are shared and never scaled, so the mine’s authored totals stay their reference.
   * Rock HP is never scaled by party size. A crew of six clears rock faster, and the bigger night that follows is the balance.
* Multipliers are sublinear: six players are not six times as effective.
* The count is sampled once per day cycle at dawn, never continuously, so no wave changes under a player. The day-start message states it plainly (“Crew of 4. Waves 2.0x”).
* The scaling count only ever goes down after a run starts. A player leaving eases the run at the next dawn; nothing ever gets harder mid-run.
Resources
* The game has 3 Resource Types
   * In-Run Raw Resources
   * In-Run Refined Resources
   * Meta Currency 


Raw Resources
These are resources harvested directly from mining. They are not useful until they are refined into In-Run Currency via the Refinery. 


* Iron Ore: Dropped from breaking an Iron Block. Refined into Iron Bars. 
* Gold Ore: Dropped from breaking an Iron Block. Refined into Gold Bars. 
* Uranium Ore: Dropped from breaking a Uranium Block. Refined into Uranium. 
Refined Resources
These are resources that have been refined from Raw Resources via the Refinery and can be used by the player. 


* Iron Bars: Refined from Iron Ore. Goes into a private player balance, but is spent on shared items like wall repairs and defenses. Since M63 (2026-10-11) Iron buys every defense purchase: Towers, Traps, fortification donations, repairs, Post Weapon upgrades, and handheld Weapon upgrades. Since 2026-10-05 (M32) a player can give Iron Bars to a crewmate: the "Give Currency" prompt on any other player opens a menu with a Gold row and an Iron row (plus and minus step by 1, held they repeat faster; the amount can be typed), a Send button, and a confirmation page; Confirm moves the bars, both players see them fly between the two characters (the Refinery's flight), the sender hears each bar go and the receiver hears the Refinery payout and sees the balance row bump, and both get a line ("[DisplayName] sent you 20 Gold Bars and 10 Iron Bars"). Dead players can neither send nor receive
* Gold Bars: Refined from Gold Ore. Goes into a private player balance and is used on personal mining upgrades only since M63 (2026-10-11): Pick Axe, Boots, Backpack, Jet Pack, Compass, Geiger Counter, Torch, Dynamite. Post and Weapon upgrades cost Iron since then (Gold before), so a player never weighs a pick against a post rung; the choices live inside each currency instead (what to buy first with Gold; who in a crew builds what with Iron). Can be given to a crewmate the same way as Iron Bars (M32)
* (Diamonds were refined from Crystals into a shared Camp Level pool until 2026-10-06, M33; both are gone, and Diamonds is now the name of the lobby currency below)
* Uranium: Refine from Uranium Ore. This is the win condition. Getting X amount of Uranium allows players to call in a rescue helicopter. 
Meta Currency
These currencies survive a run and are used to buy permanent unlocks/upgrades/etc from the lobby store


* Diamonds: Earned by reaching specific milestones in a run or by purchasing with Robux
Camp Locations
Every camp consists of a few primary structures, each with a different purpose:
Mines
* Every camp has a mine: one open volume of rock behind a short entrance tunnel, sealed in bedrock
* Players can dig in any direction from the entrance; there are no walls, gates, or set paths inside
* The mine is authored as depth zones: the deeper a zone, the harder its rock and the more valuable its ore and uranium
* Pre-carved pockets (small caverns with ore on their walls) are scattered through every zone, so digging finds things and a crew has reasons to call each other over




Refinery
* Located just outside the mine entrance is the Refinery
* Players bring their raw materials here to get refined
* Under attack (2026-09-25): while any live monster is within 20 studs of the Refinery (GameData/Camp/Structures REFINERY_ATTACK_RADIUS_STUDS, checked four times a second) every client hears the RefineryUnderAttack siren once per red flash of the Refinery HP bar (M33; a loop until then), and the red alert "The Refinery is under attack" shows once as the attack begins; the state clears, and the siren stops, once the last monster leaves the radius. Since 2026-10-08 a monster’s hit landing on the Refinery also holds the state on for REFINERY_ATTACK_HOLD_SEC (5 s) whatever the distance, because a Flyer shells it from outside the radius and night 7 of the fifth M34 run was lost in silence. The state is cleared the instant a night ends or the wave is wiped (2026-10-21; the 5 s hold had run the siren into the day)
* It functions like a simulator game, players walk up to the refinery and, as soon as they step inside the ring drawn on the ground around it (REFINE_RADIUS_STUDS, 14, GameData/Refinery; decided 2026-10-01, replacing the "Refine Raw Resources" proximity prompt; the ring shows only while the player carries ore and fades out as the Refinery pulls the last of it, 2026-10-02), all the raw resources are sucked from the player into the Refinery, which spits out the appropriate refined materials, which go straight into the player balance for spending. 
* The Refinery is the focal point of the camp: its HP bar floats above it and if destroyed, it ends the game
* Players must protect the refinery at all costs

Tools
Tools are items that allow players to perform an action when equipped. Players load in with a weapon, a pick axe, and a hammer as their primary tools, but can buy other tools from the in-run stores. 
Tool Bar System
* The tool bar is a custom tool bar that mimics the functionality of the standard Roblox tool bar, but displays more than 3 items on mobile and keeps item order intact. 
* When a player has a tool, it appears in their tool bar at the bottom center of the screen
* When a player taps the tool in the tool bar, that tool is equipped
* Only one tool can be equipped at a time
* Tapping another tool or tapping the currently equipped tool in the Tool Bar unequips the currently tool 
* Keyboard: keys 1-9 toggle the slot with that number. Gamepad: the bumpers step through the bar; stepping past either end unequips. The number hint on each slot is shown only when a keyboard is present
* The bar shows what the server says the player holds (tool slots and the equipped tool are server state replicated as attributes); every tap is a request. The bar slides away while a menu is open
* The held model is a real Roblox Tool (decided 2026-09-15, as in the reference games): the server builds it from the GameAssets/Tools template when a tool is equipped and destroys it when not, so the Humanoid grips it, plays the arm pose and the forward swing on every use, and keeps it visible in first person. The Tool is only the visual; slots and counts stay in server Lua state and it is never stored in the Roblox Backpack (a Roblox-side unequip counts as an unequip request). Roblox's own hotbar is switched off
* Consumables (Torch, Dynamite) show how many are held as an "xN" badge on their slot and leave the bar when the last one is used; a class's own consumable (the Demolitionist's dynamite, 2026-10-20) stays in the bar at x0, greyed, with its grey sheet draining down over the wait for the next, and a tap on it says how long is left. Slots sit in a fixed order whatever order they were granted: pick axe, weapon, torch, gadget, repair, dynamite last (2026-10-20)
* Every slot shows its tool's picture (shared Icons, TOOL by tool kind, WEAPON by weapon kind, and GADGET by gadget kind; one picture for every pick axe level), with the name standing in only for a tool without one (decided 2026-09-21), and an action word under the slot saying what the tool does, never what it is: MINE, SHOOT, LIGHT, BLAST, REPAIR, BUILD (2026-09-25). The backpack button and the jet pack bar carry pictures the same way
* The Defenses tool is gone (decided 2026-09-30): Build Mode is entered at the Defense Table in the Defense Store instead (see "Building Towers")

Hammer (Default Tool)
* Every player also starts every run with a Hammer (decided 2026-09-17)

A wall's or the gate's bar always draws on top of the world (decided 2026-09-30: it hangs at chest height inside the thick wall); the Refinery's and a Tower's draw on top only at night, so a miner cannot steer by the Refinery's bar to find the way out. Weapon (Default Tool)
* Every player also starts every run with a weapon
* Players can choose which weapon they bring on a run via the loadout menu in the lobby
* The default weapon is a Rifle
* Equipping the Weapon puts the player in Weapon Mode, allowing them to use the weapon to fight enemies
* This is helpful for early enemies and any monsters that get into the base or spawn in the mines
* As built (M24): the weapon is the second tool bar slot, named for what is carried (“RIFLE”). Weapon Mode shows the reticle and an ammo readout above the tool bar (“3 / 5”, or RELOADING). A press fires once and holding repeats, on every input type, exactly like mining (click, gamepad trigger, the touch action button, or a resting touch). R, gamepad X, or a tap on the ammo readout reloads, and an empty magazine reloads by itself. A reload keeps running if the player swaps tools
* Bullets fly through the fortifications (decided 2026-09-30): a hitscan shot from a handheld weapon or a post ignores the walls, the posts, the gate, and the mounted guns, on the server and in the tracer, so a post covers every wall of a curved line and a crewmate on the next post is never in the way. Rockets still burst on them
* Every weapon is hitscan with a magazine and unlimited reserve ammo (decided 2026-09-17). The Rifle is a lever-action to match its art (decided 2026-09-17): 5 rounds, a shot every 0.6 s, 60 damage (doubled from 30, 2026-09-24), 300 stud range, a 2.5 s reload. All weapon numbers live in GameData/Weapons/Handheld, one entry per weapon
* Every shot is a request carrying only the ray the player aimed; the server checks the weapon is equipped, loaded, and off cooldown and that the ray starts at the shooter's head, then decides the hit itself. Only registered damageable targets can be hurt (a dev-tool Target Dummy until Monsters exist); players and camp structures can never be shot. The mine's rocks exist only on clients, so they stop a tracer but not the server's ray; revisit when monsters can be in the mine
* First-person feel (decided 2026-09-17): the gun on screen is a viewmodel, a copy of the weapon locked to the camera so it always follows the reticle, with sway when turning, a walk bob, a recoil kick on each shot, and a lowered pose while reloading. The real held Tool is hidden for its owner only. Other players see a crewmate lean and tilt their weapon up and down with their aim (the look pitch is replicated a few times a second, cosmetic only). Mounted Post weapons reuse the same aim replication and muzzle conventions
* Shot feedback: a short tracer streak flies from the barrel tip to the hit point (a full-length beam was tried and looked left behind when strafing), a 0.125 s muzzle flash light and a 0.1 s puff of muzzle smoke at the barrel, a small dust puff where the bullet lands, and a bullet hole decal that fades out after 10 seconds. Holes are never left on things that move or vanish (targets, players, a rock that is then mined)
* Authoring: weapon art lives in GameAssets/Weapons and is never edited by code; the held model GameAssets/Tools/WEAPON_<KEY> is built from it by scripts/studio/build_tool_templates.luau (scaled to hand size, an invisible Handle at the grip, a Muzzle attachment at the barrel tip carrying the MuzzleFlash light and MuzzleSmoke emitter). The bullet hole is the Decal GameAssets/Effects/BulletHole
* Sounds: every weapon has its own four sounds, never shared ones (decided 2026-09-17): <Weapon>Fire (3D from the barrel tip, full volume within 30 studs and fading out by 400 so a crewmate across the camp is still heard), <Weapon>Reload, <Weapon>Empty (the dry click), and <Weapon>Hit (the shooter's hit confirm). The Rifle's are RifleFire, RifleReload, RifleEmpty, RifleHit

Mining
Mining is half the game and is the only way players can win a run. However the goal is to keep mining simple, lightly strategic, but tactilely rewarding. Every mine is randomly generated based on a set of parameters created for each map/difficulty level. We want mining to feel exactly like mining in Roblox, so players just intuitively know how to mine. 


Rocks
Every mine consists of a grid of cube Rocks (4x4 Studs). A passage has to be two Rocks tall for a player to walk through (decided 2026-09-29): Roblox lets only an R15 character's torso collide, so a one-Rock hole let the head into the Rock above and the camera into the unrendered mine behind it; every character now carries an invisible collider over its head (ClearanceManager, GameData/Mining/Clearance) that a one-Rock hole cannot admit. Every Rock will use the same 4x4 cube mesh, but will have a different texture based on the Rock Type. Every Rock mesh will be located in ReplicatedStorage/GameAssets/Rocks (the central asset folder) named by its RockName enum key (IRON_3, STONE_1, BEDROCK); the player-facing name (“Iron 3”) is the enum’s public name. Clients clone from here; the server never holds rock parts.  
Rock Types
There are three types of Rock: Filler Rock, Resource Rocks, and Bedrock.  
Filler Rock
These Rocks do not give any resources, but fill empty space and slow progress. The vast majority of the mine will be filled with Filler Rocks. All Filler Rocks are breakable, but some are harder to break than others:


* One filler rock, Stone, in five tiers (decided 2026-09-15: several filler kinds did the same job and made ore harder to spot). Same mesh, darker as the tier rises
* Stone 1 (10 HP)
* Stone 2 (20 HP)
* Stone 3 (40 HP)
* Stone 4 (80 HP)
* Stone 5 (160 HP)
Resource Rocks
These Rocks give any raw resources when destroyed. More valuable Resource Rocks appear more often in deeper zones. Resource Rocks also have multiple tiers, with higher tiers taking longer to break but giving more resources: 


* Iron
   * Iron 1 (15 HP, 3 Iron Ore)
   * Iron 2 (30 HP, 10 Iron Ore)
   * Iron 3 (60 HP, 29 Iron Ore)
   * Iron 4 (110 HP, 78 Iron Ore) 
* Gold 
   * Gold 1 (20 HP, 3 Gold Ore)
   * Gold 2 (40 HP, 10 Gold Ore)
   * Gold 3 (75 HP, 30 Gold Ore)
   * Gold 4 (140 HP, 87 Gold Ore) 
* Uranium 1 / 2 / 3 (100 / 300 / 600 HP for 1 / 3 / 6 Uranium Ore; three tiers since 2026-10-26, one rock at one ore before)


Bedrock
Bedrock is a Rock that cannot be destroyed by anything, but is used to define the boundaries of the mine. Every mine will be fully surrounded by bedrock on all sides (except for the entrance), which ensures players cannot dig out into some unwanted area.  
Mine Layout
* The mine is one open, explorable volume. Decided 2026-09-15, replacing sealed chambers: chambers made mining linear and killed the “look what I found over here, help me” moment, which needs room to split up and things to find
* Depth zones: the mine file is an ordered list of zones running back into the mountain, and each zone sets how hard the rock is, which ore tiers dominate, how much ore and uranium it holds, and how many pockets it has. Rock gets harder and ore gets better the deeper a crew digs
* Soft gating: nothing in the mine is ever locked. A starting pick axe against deep rock is a wall the crew can feel without a wall being there, and the Gold price ladder of the pick axe is what paces depth (the Camp Level gated the pick axe tiers until it was removed, 2026-10-06)
* Pockets: pre-carved caverns of a few blocks, with ore exposed on their walls, scattered through every zone. They are what digging discovers and what a crew talks about. Tripled on 2026-10-06 after the first M34 playtest (12 / 18 / 24 / 30 / 30 per zone on Deadman's Canyon, from 4 / 6 / 8 / 10 / 10) and wider the deeper the zone, in small steps (radius 1 to 2 blocks in zone 1, 2 in zones 2 and 3, 2 to 3 in zones 4 and 5 since the second M34 playtest, where zone 5 at a fixed radius of 3 went from smallish rooms to massive ones in one step; a first try at 3 to 4 in zone 5 hollowed out 22% of it; a zone's pocketRadiusMin and pocketRadiusMax, inherited like its other values): finding one felt good, and they were rare and small. Remade as 4 by 4 rooms on 2026-10-08 with far fewer per zone (mine spec §8). Proposed the same day (M62): a 20% chance a pocket holds a zombie that hunts players before the Refinery, wandering its pocket and chasing only along a clear path
* The entrance: a short tunnel through the front bedrock into the first zone, the only opening in the shell. Past it the crew chooses its own direction
* Clear signal without walls: rock colour and material change with tier, so deeper rock looks different, and the next pick axe level is the goal to work toward
* There are 4 zones per mine, though the system needs to be built in a way that this is a customizable number
* This is to encourage players to upgrade their mining equipment as the game progresses


Mining Rock
* To mine Rock, players must first equip their Pick Axe – which puts them in “Mining Mode”
* Mining is intended to feel just like Minecraft, so it is intuitive to a broad amount of players
* There needs to be a small dot in the center screen, representing the player’s aim
* With Pick Axed equipped, any rock in the center of the players screen is highlighted (Highlight, white borders, transparent fill)  and the name of that Rock is shown to the right of the player’s central reticle over a health bar; no numbers (decided 2026-09-15, as in Minecraft and Dome Keeper: the block and the bar are the readout). The bar turns red once the block is crumbling; bedrock shows no bar  
* To start breaking the highlighted rock players:
   * Mobile (as built 2026-09-16, modelled on Minecraft Bedrock's split controls): the screen is also the camera, so a bare tap never swings. A finger that rests still in the free screen area for a quarter second starts a hold on the block under the reticle; dragging that finger afterwards turns the camera while the hold keeps mining, and lifting it ends the hold. A touch-only action button beside the jump button (labelled with the equipped tool until tool icons exist) does the same on press and hold, and is the only touch input for the torch (press places) and dynamite (press throws)
   * PC: LMB click to hit once, hold LMB to hit continuously 
   * GamePad: RT to hit once, hold RT to hit continuously 
* A held input swings every 0.45 s (hitIntervalSec in GameData/Mining/PickAxe). The reticle reaches 12 studs, the 3-block pickaxe reach the mine generator assumes. After the held block breaks, the hold waits until the reticle has rested on the next block for one interval before swinging again, so every first hit on a block is intended (decided 2026-09-16); a fresh press skips the wait
* Every swing is a request (TryHitRock with the block's grid cell). The server refuses it unless the pick axe is equipped, the cell is a diggable rock, the player's root is within reach plus a 6-stud tolerance of the block centre, and 0.35 s have passed since that player's last accepted swing. Damage is the pick axe level's value; the server then tells every client the block's remaining HP (crack state) or that it broke
* Until M46 art, the crack overlay is a placeholder tint: the block darkens at 60% and again at 30% HP. Hit and break bursts are placeholder particles in the block's colour; the RockHit sound (filler) or ResourceHit sound (ore, metallic) plays on a hit and RockBreak on a break, for players within 60 studs
* Only the Rock currently highlighted will be hit 
* The Rock’s health bar is updated to reflect its current health after each hit
* There will be a particle effect with each hit (rock pieces flying) and noises to make it feel tactile and satisfying 
* Once the Rock’s HP is at or below 0, it breaks
* If any Ore is inside, it drops out (see Collecting Ore below) 
* Players can mine as much a they want, they just can’t collect any additional Ore if their Backpack is full
* A backpack icon with current status is always shown in the HUD (taken slots/total slots), on the right edge a little above mid height with the jet pack fuel bar directly under it (decided 2026-09-15; it was Mining Mode only). The balances panel sits on the left edge at the same height; neither may sit where the chat window, the top bar, the thumbstick, or the jump button can cover it (GUI rule, 2026-09-16). On touch the stack is pinned directly above the Jet Pack button. The Roblox player list is off in the gameplay place (2026-09-16)
* When the Backpack is full, the Backpack Icon/numbers should turn red and a small text label should say “Backpack full” (see “A Game About Digging a Hole” for reference), and the Fail sound plays once on the change to full
Collecting Ore
* Dropped resources are automatically given to the player who breaks the block. 
* Any resources that the breaker doesn’t have room for in their Backpack (raw resource inventory) is dropped on the ground
* Dropped Ore is automatically picked up by any player who walks over it with empty Backpack space (like Minecraft)
* When Ore is collected, it should make a pop sound, again like Minecraft
* Players can tap their Backpack icon to bring up a Backpack inventory menu
* This menu shows how much of each Ore is in their backpack (only showing Ore that the player actually has) 
* Capacity is counted in ore units, so the HUD’s taken/total is total ore over capacity (“12/16”). Contents, level, and capacity are server run state replicated as private attributes; the backpack HUD button is always shown and opens the contents menu as an overlay
* A broken resource rock gives the breaker its yield. Iron and Gold are multiplied by the party table (PartyScaling) and rounded half up; Uranium never is. Party size is the crew count RunCycleManager samples at run start, every dawn, and on every departure (M28; departures 2026-09-25), never the live player count
* Ore that does not fit lands by the block as a pickup (one invisible server part carrying resource and amount; clients draw a bobbing cube in the ore’s colour; a dropped uranium pickup hums the UraniumHum loop within 15 studs, like exposed uranium rock, 2026-10-07), scattered up to 1.5 studs and settled onto the ground beneath (inside the mine the server walks the grid column down to the next rock; outside it raycasts the camp), so drops never hang where the block was. Ore at the player's feet still flies into the HUD backpack from the nearest screen edge. Any player with room within 5 studs collects it, partial amounts included; the server checks four times a second. A pickup nobody takes disappears after 120 s, and past 300 pickups the oldest go first (GameData/Mining/Backpack) Since 2026-09-29 the icon on each face of the plate is a SurfaceGui with LightInfluence 0 (the OrePickupFace template under GameAssets/Gui) rather than a Decal, so it reads as bright underground as the flying icons do.
Refining Ore
* Players refine Raw Resources by taking them to the Refinery
* The Refinery is the main camp building, located just outside the Mine Entrance
* It is a complicated looking machine, that grinds up Raw Resources and returns them as Refined Resources that can be spent
* The goal is to keep this very simple and recognizable to anyone who has played a Roblox simulator where you exchange resources for currency
* Players simply walk into the ring around the Refinery with ore in the backpack; the server checks for that four times a second (REFINE_POLL_SEC) and refines them on the spot, one player at a time while the machine grinds (decided 2026-10-01; it was a "Refine Raw Resources" proximity prompt before) 
* Triggering the proximity prompt begins the refining process
* All Raw Resources in the player’s Backpack are automatically refined at the same time
* Icons for each Raw Resource in the players backpack are sucked out of their backpack and into the Refinery mouth
* The Refinery spins and grinds the resources for a few seconds and spits out icons for each of the Refined Resources it generates, which should fly into the player’s HUD to the appropriate balance bar. As built 2026-10-09: the designer's Refinery model carries a Funnel with Entrance and Exit attachments and two grinder rollers (Spikes1, Spikes2). Ore icons fly into the Entrance; as the first lands the rollers counter-rotate about their long axis (180 degrees a second, with the gears welded to them) and the RefineryGrind loop plays 3D from the Funnel (full to 6 studs, silent at 25) on every client, whoever is refining; both stop at the payout, when the bars fly out of the Exit. A refine takes 4 seconds (REFINE_DURATION_SEC; 2 before)
* The balance bars should shake and update as each icon hits it
* This process should all feel very satisfying, both visually and audibly – lots of particle effects, sounds, etc
* As built (M20, decided 2026-09-14): every ore refines one to one (GameData/Refinery, adjustable per ore). The prompt is heard by the server directly, never as a client message; it empties the whole backpack, disables itself for a 2 second grind, then pays out. Iron Bars and Gold Bars are private per-player balances; Uranium goes into the shared rescue count shown to every player (Diamonds went into the shared Camp Level pool until 2026-10-06, M33). Randomized Mine Creation


1. What a mine is
A mine is a single grid of 4×4×4 stud cube blocks, generated on the server when a run starts. It is never built by hand in Studio.
The grid is one open volume of rock inside a bedrock shell, entered through a short tunnel at the mouth. It is authored as zones: consecutive depth bands running back into the mountain, each setting the rock mix, ore, uranium, and pocket count for its band. Nothing inside the mine is walled or gated; the deeper rock is simply harder (decided 2026-09-15). Every uranium rock hums (Sfx.UraniumHum, a 3D loop, full volume within 4 studs and silent past 20; GameData/Mines/Streaming), buried or exposed, so a crew can find the win condition by ear through solid rock and the depth HP curve stays the pacing (decided 2026-09-25). Client side only: one looping player feeds an invisible emitter per uranium rock within 6 blocks of the player, kept with the block stream, so the cost is a handful of voices at most.
Pockets are small caverns pre-carved into each zone so ore is exposed on their walls and there is something to discover.
Pocket lurkers (M62, 2026-10-08): a fixed number of pockets hold a Cave Spider, 10 for a solo player and 2 more per extra crew member, 20 at most (GameData/Monsters/Lurkers BASE_COUNT, COUNT_PER_EXTRA_CREW, MAX_COUNT; decided 2026-10-08, replacing a one-in-five chance that swung from run to run), chosen from the mine’s seed among the pockets of the designer’s zone 2 and deeper, the first iron band (MIN_ZONE_INDEX 3 in the mine file’s numbering since 2026-10-23; 4 from 2026-10-08, when the first three zones were spider-free so a new player learned the mine before it bit back; now the first two are). The first block broken within a cell of the pocket’s room wakes it. It crawls the mine’s surfaces (an air cell is walkable only when it touches rock, six ways, no gravity: that is what makes it cheap, no path field and no raycasts; designer 2026-10-08, after a first version that cut through open air and clipped corners), hunts players only, never leaves the mine, never counts toward a wave, and hunts by day and by night. It stays on the floor and climbs a wall only where the route needs it (a climb step costs 3 against the floor’s 1 in the search; a single cell of open air, one that touches no rock on any side, is leapt at a cost of 5 and only from a cell on rock, never two in a row, because one such cell where a wide tunnel met a room’s wall sealed a spider in its room on 2026-10-08), walks cell to cell along a cheapest-first search of up to SEARCH_MAX_CELLS (24 since the rooms grew, 12 before) toward a player it can see or last saw, and with nothing to chase it drifts to a neighbouring floor cell. Speed 9 against the player’s 16, so it is outrun on open ground and caught in a dead end or by surprise. It takes five bites over twelve seconds to kill a fresh player (three in 2.4 s until 2026-10-08) and is beaten by anyone with a weapon rung or two, so opening a pocket early means running and coming back armed (designer’s pick). The Camp Map follows it like any monster. The spawn is the floor cell of the room farthest from the block that woke it (the nearest floor cell earlier on 2026-10-08, its ceiling before that), so the player sees it across the room and has a moment to react. The Monsters dev panel’s “Show Cave Spider spawns” hangs a red SPIDER SPAWN billboard (GameAssets/Gui/SpiderSpawn, always on top, seen from 400 studs) over every sleeping pocket’s resting cell, so a tester can walk straight to one; a marker goes when its spider wakes, and the toggle survives a new run. A sleeping pocket skitters every 10 s (the walk sound, 3D from where the lurker rests, heard to 20 studs) to any player that close, so a careful player hears one before opening its wall; the server plays it, so no client learns where the pockets are. A pocket wakes only when the broken block opens into its air (a block touching it at a corner woke a lurker into a sealed room on 2026-10-08), and a lurker that cannot reach its player finishes its walk and drifts rather than freezing.
Mine monsters (M68, designed 2026-10-26): two more live in the mine beside the Cave Spider, one you beat by restraint and one by running, both drawn as flat images with effects round them. The Seam is a face in a block that never attacks and bursts on whoever breaks it, drifting over the mine’s surfaces and spreading onto stone, 50 of them from zone 2 down, safely cleared only from a distance; the Drag sleeps sealed in three deep pockets, wakes when one is opened, and hunts its waker through the open air of the mine at just under a player’s run, unhurtable inside and burning away the moment it is led out of the mine’s mouth, day or night. Both are detailed under “Monster Types”.
A designer authors roughly 40 numbers per mine. Difficulty is one more.

6. The weight kernel
hardness and tierBias both compress a set of weights into one number, and they use the same function. Build it once.
weights(center, count, spread = 1.2):
    for i in 1..count:
        w[i] = max(0, 1 - abs(i - center) / spread)
    normalise w so it sums to 1
    return w
spread is a global tuning constant. It controls how much neighbouring categories bleed in. At spread = 1.2 (decided 2026-09-15; 1.5 put too much tier 2 next to the entrance):

	Note that spread = 1.2 with whole-number hardness means a zone is three quarters its own tier with an occasional block of each neighbour, so “the rock gets harder as you go deeper” reads zone by zone. Raising spread toward 1.5 blends neighbouring zones into each other. Tune it once, globally, after seeing a mine in-game.
Do not drop spread toward zero. At spread = 1.0 a whole-number hardness produces a zone of one single stone tier, which reads as flat and artificial. The bleed is what makes rock look natural.
tierBias works identically over the four ore tiers. A zone’s iron = 30 with tierBias = 2.0 places 30 iron clusters split 4 / 22 / 4 / 0 across tiers 1–4. Fractional splits use largest-remainder rounding so the tiers always sum to exactly the authored count; a tie goes to the lower tier.
Uranium ignores tierBias; each tier’s count (uranium, uranium2, uranium3) is placed directly, and the supply checks count ore, not rocks. Ore tiers also climb with depth (decided 2026-09-28): GameData/Rocks/Weights TIER_MIN_DEPTH_BLOCKS (0 / 14 / 44 / 68) is how many blocks from the mouth each tier may first appear, a cluster whose tier is not allowed anywhere in its zone drops to the deepest tier that is, and within a zone the tiers above its bias sit in the back half and the tiers below it in the front half, so the first rows are tier 1 only and a Gold II vein is never a few blocks in.

8. The entrance and pockets
The entrance is the only opening in the bedrock shell: a tunnel entranceWidth blocks wide, centred on the centreline, entranceHeight blocks up from the floor, carved through the front bedrock and entranceDepth blocks into zone 1 so a crew can walk in and choose a direction.
* An even width cannot centre on a single block, so it leans one block toward positive width.
* Keep the height at or below pickaxe reach (~3 blocks) unless climbing is a real mechanic, or the tunnel has a ceiling players can see but not touch. The generator warns.
* Past the tunnel a player faces solid rock in every direction. That is the point: from here on the crew makes its own tunnels.
Pockets are pre-carved caverns: per zone, pockets rooms of air with a half-width drawn between pocketRadiusMin and pocketRadiusMax, dropped at random inside the zone. Since 2026-10-08 a pocket is a room, not a sphere: a square footprint 2r blocks on a side standing on a flat floor, 2r-1 rows tall, with the top row stepped in by one block so the ceiling domes rather than boxes. The designer’s rule is a floor of at least 4 by 4 blocks (radius 2, 36 cells, 16 studs across and 12 tall; 5 by 5 for a few hours the same day, too big in play): the radius 1 spheres before it (6 cells after their pit was filled the same morning) were so small that a Cave Spider woke right in the face of whoever opened one and a pocket never read as a cave. Every zone on both mines is radius 2 now, and the counts came down to match (Deadman’s Canyon 1 / 3 / 5 / 9 / 13 / 15 from 4 / 20 / 18 / 24 / 30 / 30, about 5% of each zone as air, the same share the small ones had in the early zones). They are carved before veins, so ore lands around them and never inside them, and every pocket wall is a discovery. A pocket a player breaks into is the “look what I found” moment the open mine exists for, so a zone with no pockets is a uniform block that only ever gets tunnelled.
Pocket count is the strongest single lever on how a zone plays: a few big pockets read as caverns, many small ones as honeycomb. Zone height and pocket count together decide how much of a zone is actually reachable from a standing start; the report shows both.

10. Generation pipeline
Ordered. The order is load-bearing and each step explains why.
1. Resolve difficulty. Apply §7 to produce effective hardness and vein counts.
2. Resolve inheritance. Walk the zone list, filling unspecified values from the previous zone, then from mine defaults.
3. Validate. See §11. Fail loudly before spending time generating.
4. Size the grid.
gridDepth  = frontBedrock + sum(zoneDepths) + farBedrock
gridHeight = max(zoneHeights) + floorBedrock + ceilingBedrock
gridWidth  = max(zoneWidths) + sideBedrock * 2
5. Fill the entire grid with bedrock. Everything is solid until carved. This is what makes “sealed on all sides” the default state rather than a rule to enforce. A zone narrower or shorter than its neighbour simply has thicker bedrock around it, with no special handling.
6. Fill each zone with filler rock. Roll each block of the zone’s volume against the §6 hardness weights. Zones abut, so no bedrock ever stands between them.
7. Carve pockets. Per zone, pockets rooms of air (see §8) at random positions inside the zone, half-width between pocketRadiusMin and pocketRadiusMax. Before veins, so ore lands around pockets and never inside them.
8. Stamp generated veins. Per zone, per resource: split the count across tiers by tierBias, place each cluster at a random rock position inside the zone, respecting veinEntranceClearance and skipping pocket air. Uranium is stamped last and gets one guarantee ordinary ore does not, because it is the win condition: no uranium rock lands on another, so placed always equals authored. It may sit at any height in the zone (decided 2026-09-29; until then it was held within pickaxe reach of the floor, a rule from before the Jet Pack existed, and it packed the deep zones' uranium into their lowest rows). Since 2026-09-28 each cluster's tier is also held to its depth floor (TIER_MIN_DEPTH_BLOCKS) and to its half of the zone (above the bias in the back half, below it in the front), see tierBias above.
9. Stamp hand-placed rock. After generated veins and pockets, so it always wins.
10. Carve the entrance. After veins and hand-placed rock, so nothing can plug the mouth. It is the only opening in the shell.
11. Report. Log the seed, grid size, per-zone diggable volume and pocket volume, and derived ore totals per zone, both requested (vein counts × tier split × mean cluster size × yield) and actually placed, since overlapping clusters overwrite each other and silently lower the count. Also report how much of each zone’s diggable volume sits within pickaxe reach of the floor, so a zone that is mostly decoration is caught in the log rather than in playtest. Also report cumulative uranium per zone (“uranium so far”) so the designer can see the counter’s progression against uraniumTarget. The designer authors vein counts but cares about ore, so the generator has to close that loop.
After the report, check the grid itself: if fewer uranium rocks survived than the largest party needs, refuse the result and name the seed. Validation checks the authored numbers; this checks what was actually built, so no seed can ever ship unwinnable.
Randomness. One Random is seeded from the run seed, and each zone draws from its own sub-seed derived from the run seed and the zone index. Changing zone 2’s numbers therefore never reshuffles zone 1, so a designer sees only the effect of their edit.

11. Validation
Every check must name the parameter and the zone, so a misconfiguration is identifiable without reading code.
Fatal — refuse to generate:
* The authored uranium total is below the map’s uraniumTarget × the largest party multiplier. The run is unwinnable for a full crew
* A zone has a dimension below 1, or a negative pocket count
* entranceWidth or entranceHeight exceeds zone 1, or entranceDepth exceeds zone 1’s depth. The mouth would cut bedrock
* pocketRadiusMin is negative or pocketRadiusMax is below it
* facing is not one of the four permitted values
Warn and continue:
* entranceHeight is above pickaxe reach with no climbing mechanic enabled
* A hand-placed entry falls inside the entrance tunnel. It will be carved away
* A hand-placed entry falls outside its zone bounds
* Pockets and the entrance leave a zone with no diggable volume
* hardness outside 1.0–5.0 (one per stone tier) or tierBias outside 1.0–4.0 (one per ore tier). Clamp

12. Runtime
Camp level. Removed from the game on 2026-10-06 (M33) along with Crystal and the in-run Diamond; the pacing beat of a run is now the pick axe ladder and the fortification tier, which is announced to the whole crew the way the camp level was.
Damage. Rock HP is tracked server-side by grid position, not on the rendered block. Blocks are pooled and streamed, so a part that showed a half-mined block may be recycled or unloaded; damage keyed to position survives both.
Visual damage states. Three states per the GDD: untouched, 60%, 30%. Author these as a crack overlay applied on top of any rock, not as separate textures per rock type. Seventeen rock types × 3 states is 51 assets to author and maintain; a shared overlay is 2, and it works automatically on rock types added later.
Designer tooling. A dev tool regenerates the mine in a running session, with an optional seed, without restarting the run. This is the tuning loop: edit the mine file, sync, regenerate, walk in. A pure expected-ore preview computes the report’s requested-ore and HP totals from the mine file alone, so a designer can read the balance sheet of an edit before generating anything.
The run report (M34, 2026-10-06): at every dawn the server Output prints the day just closed, per player (Iron, Gold, and Uranium refined, Refinery trips and the average time between them, towers built and upgraded with the Iron spent, Hammer repairs, kills, damage given, Diamonds earned) and for the night (its length, kills, wall damage, walls lost, Refinery damage); the whole run with totals prints when the run ends, and the Run dev panel's "Print the run report" button prints everything so far. It exists to calibrate the balance model against real play. Since 2026-10-08 each player also gets a second line (seconds in the mine, manning a post, and in camp, sampled every 2 s and not counted while the run is paused; pick axe swings and breaks by stone, gold, iron, and uranium; the deepest block hit and its zone; deaths, revives, damage taken; every named purchase in order, a run of the same one collapsed to a count) and each fought night a detail line (groups, the generator's target, seconds from the last group's arrival to the field clearing, placements lost, damage by structure and by monster kind, biggest first). The same day the run record: at every dawn and at the run's end the report's rows are saved as one entry per run in the DigDefendRunRecords DataStore (about 1 KB a day; a 16-day solo run is 18 KB), stamped with the place version, a fingerprint of every GameData table (so runs on different tuning are never averaged together), and the count of dev commands used; players are crew slots 1 to 6, never a UserId or a name, so the store holds no personal data. scripts/studio/pull_run_records.luau prints every run and per-day averages over a filter, so testers' runs can be read beside the designer's.
Open questions, to revisit only on real feedback:
* Independent per-block filler rolls may read as static noise rather than strata. If so, roll per 2×2×2 cell or bias toward a neighbour’s rock. Visual only; balance is untouched.
* Fixed layout may feel same-shaped after many runs. Pockets already vary per seed; if the envelope itself needs to, add bounded jitter to zone depths rather than freer generation, so balance stays authored.

13. Worked example
A four-zone mine. Note how short zones 2–4 are — everything unspecified is inherited.
return {
    mineId = "canyon_default",
    seed = nil,
    origin = Vector3.new(-359.259, -6, -20.911),
    facing = "-X",

    bedrockThickness = 1,
    entranceWidth = 3,
    entranceHeight = 3,
    entranceDepth = 3,
    veinEntranceClearance = 4,
    goldOnlyEntranceRadius = 16,
    pocketRadiusMin = 1,
    pocketRadiusMax = 2,
    uraniumTarget = 35,

    defaultZoneHeight = 8,
    defaultZoneWidth = 24,

    zones = {
        {   -- 1: soft, generous, everything reachable
            depth = 20,
            hardness = 1.0,
            tierBias = 1.0,
            iron = 34, gold = 12, uranium = 6,
            pockets = 2,
        },

        {   -- 2: mixed rock, better ore
            depth = 24,
            hardness = 2.0,
            tierBias = 2.0,
            iron = 30, gold = 18, uranium = 9,
            pockets = 3,
        },

        {   -- 3: taller, harder
            depth = 24,
            height = 12,
            floorDrop = 6,
            hardness = 3.0,
            tierBias = 3.0,
            iron = 22, gold = 22, uranium = 9,
            pockets = 4,
        },

        {   -- 4: cathedral, the deepest and richest rock
            depth = 28,
            height = 16,
            floorDrop = 8,
            hardness = 4.0,
            tierBias = 4.0,
            iron = 16, gold = 20, uranium = 111,
            pockets = 5,
        },
    },
}
Uranium is spread 6 / 9 / 9 / 111 against a solo target of 30, so the first three zones each hold 20%, 30%, and 30% of the solo target and the counter moves from the first zone; zone 4 holds the rest and covers the worst case (30 × 1.3 Nightmare × 3.5 six players = 136.5, rounded to the nearest 5 = 135). Nothing stops a crew tunnelling straight for zone 4, except that its rock is hardness 4.0 against a level 1 pick axe; that curve is the pacing. As of 2026-09-28 the file authors 9 / 14 / 20 / 950 against a solo target of 40, iron 64 / 64 / 64 / 48 and gold 136 / 136 / 136 / 104 single-block veins, and pockets 4 / 6 / 8 / 10 (doubled): a player who hunts the hum takes nearly every shallow uranium rock, so the first three zones hold about one target between them for a day-10 finish,; crystal was dropped from every zone on 2026-09-29 and removed from the game on 2026-10-06.
As of 2026-09-15 the live file (GameData/Mines/DeadmansCanyon) also drops each zone below the entrance floor (floorDrop 2 / 4 / 6 / 8; since 2026-10-06 every zone is split evenly about the floor line, 5 / 6 / 9 / 12 / 13 rows above and the same below, so the mine goes down as much as up; the starter band drops only 2 since 2026-10-08) and evens out zones 1 and 2 to 22 iron / 20 gold and 22 / 22, because Gold feeds the store now while Iron's sinks (walls, traps) arrive later.
Darkness: the mine is lit by the client, not the sun. From the mouth to 100 studs in, each client blends the sun, ambient, and skybox light down to near black by how far along the mine's forward axis its character stands (ClientMineLightingManager), so torches are what light the deep mine and walking out never shows a step. Every exposed block of the starter band and zone 1 (the first 20 blocks of depth on Deadman's Canyon) is drawn at any distance and kept first within the render budget, so the mine never reads as empty from the camp (2026-10-21; before, nothing drew until the player was within the 24-block streaming radius).
* Outdoors (2026-10-21): the OutdoorAmbience loop (SoundService.Music, 2D, authored at 0.3) plays while the player is out of the mine and fades out over 1.5 s as they step into the mine's grid and in over 3 s as they step out (ClientAmbienceManager, decided on each client from its own copy of the grid with the run report's cell test, MineSpace.containsPosition); the fade carries on from whatever volume it has reached, so a quick back and forth through the mouth never jumps or restarts it Through the night it sits at half its volume under the night song, eased down over 3 s as night falls and back up over 1 s at the night's end (designer, 2026-10-21).
At Nightmare (vein divisor 1.4), the same file generates zone 2 with the same rock, 21 iron and 13 gold veins, and unchanged uranium. No second file, no overrides.
Mining Attributes


Pick Axe
* A player’s Pick Axe determines how much HP is removed from a Rock per hit
* There are 6 Pick Axe Levels since 2026-10-06 (5 before; the sixth is the late Gold sink the first M34 run was missing, and it one-shots tier 5 stone). Every level is a plain Gold purchase (the Camp Level gated level N+1 behind Camp Level N from 2026-09-15 until the gates opened on 2026-09-28 and the Camp Level was removed on 2026-10-06); the Gold price ladder is the brake
* Damage per hit by level: 5 / 15 / 45 / 135 / 400 / 1200 (each level triples, decided 2026-09-28: the mine is a simulator, small numbers first, every upgrade a jump; rock HP triples a tier to meet it; was 5 / 12 / 25 / 50 / 100) (GameData/Mining/PickAxe, DAMAGE_BY_LEVEL; the list length is the level count; level 5 is a placeholder until tuned). Level 1 breaks Stone 1 in two swings and needs 22 for Iron 4, which is what sells the upgrade. Everyone is level 1 until the Mining Supplies Store (M21), where levels 2 to 6 cost 30 / 100 / 270 / 800 / 2,400 Gold (level 3 was 90 until 2026-10-07; level 2 was 20 from 2026-10-02, tried at 15 and 20 on 2026-10-07, and settled at 30: two backpack trips, so the first buy is earned, not immediate) (tripling with the effect, 2026-09-28; level 2 was 30, then 20 from 2026-10-02, then 15 from 2026-10-07 so a new player's first run buys a pick before anything else)




Backpack
* Capacity by level, in ore units: 15 / 45 / 135 / 400 / 1,200 (each level triples, 2026-09-28; was 15 / 25 / 40 / 60 / 90) (GameData/Mining/Backpack, CAPACITY_BY_LEVEL; the list length is the level count; decided 2026-09-15 to start small so refining trips are frequent; tune in play). Five levels, each a plain Gold buy, like the pick axe. Everyone is level 1 until the Mining Supplies Store (M21), where levels 2 to 5 cost 20 / 60 / 180 / 540 Gold (2026-09-28)
Boots
* The second mining attribute, bought and upgraded in the Mining Supplies Store like the others: five levels, each a plain Gold buy. Boots only do one thing: walk speed (decided 2026-09-15)
* Walk speed by level, in studs per second: 16 / 20 / 24 / 28 / 32 (twice the step, 2026-09-28; was 16 / 18 / 20 / 22 / 24) (GameData/Mining/Boots, WALK_SPEED_BY_LEVEL; the list length is the level count; placeholders until tuned in play). Level 1 is Roblox’s default, so a new player moves exactly as they expect. Store prices for levels 2 to 5: 40 / 70 / 180 / 540 Gold (the first rung 40 and the second 70 since 2026-10-07, from 20 and 60, priced with the backpack so the pick is bought first, so the 15 pick is bought first)
* The level is run state like the pick axe level, held by the server and applied to the character’s Humanoid on upgrade and on every respawn, so nothing about speed is ever trusted from the client
* Boots change no other stat: no jump, no fall damage, no carry. Those belong to the Jet Pack and the Backpack
* Store prices for levels 2 to 5: 40 / 80 / 225 / 675 Gold (2026-10-07; the first rung 25 and the second 75 earlier that day. Day 1 gold is capped by the 15-ore pack times about five Refinery trips, near 75, so pick 30 plus backpack 40 is a full excellent day and the three first rungs can never all land on day 1; 20 / 60 / 180 / 540 from 2026-09-28: the first rung went above the 15 pick so the pick is the natural first buy, the second rung to 75 and the rest tripling from it)
Jet Pack
* The fourth mining attribute (added 2026-09-15), bought and upgraded in the Mining Supplies Store like Pick Axe, Boots, and Backpack: five levels, each a plain Gold buy. It is the climbing mechanic the mine generator has been waiting for (IS_CLIMBING_ENABLED), so mines can go taller and more vertical, and a player at the bottom of a shaft they dug has a way out
* Controls, kept to one gesture. Keyboard and gamepad: double-tap Jump and keep holding it; the jet pack burns while Jump is held and stops the moment it is released. Touch: a Jet Pack button sits directly above Roblox's jump button, the same size as it, placed against the live jump button at runtime so it can never overlap it, with the tool action button directly to the jump button's left (2026-09-16); holding it burns, releasing it stops. No hover, no descend input, no toggle state to remember: burn is up, release is down
* Fuel is the whole design. The tank starts at 1.5 seconds of burn and each upgrade adds a second (level 5 holds 5.5 seconds; doubled from half a second on 2026-09-28, with the store prices 40 / 120 / 360 / 1,080 Gold); both numbers are tunable in GameData/Mining/JetPack (retuned 2026-09-15 from 3 s plus 1 s, which cleared the mine at level 2). Fuel drains only while burning and the pack cuts out when the tank is empty, so the player falls. It refills whenever the pack is not burning, anywhere, at half a second of fuel per second, and a tank run dry locks the pack until it is full again (decided 2026-09-15, replacing an on-the-ground rule that felt inconsistent); stopping early keeps the remaining fuel. That lock is what keeps a hop from becoming flight
* Burning lifts the player straight up at a fixed climb speed (12 studs per second, so a level 1 burn lifts about four blocks and level 5 about ten, under the 72-stud mine) while the normal walk controls still steer, so a hop can be aimed onto a ledge
* The tank shows as a bar with a jet pack icon directly under the backpack button on the right edge of the HUD, always visible (decided 2026-09-15): green while the pack answers, red while it is locked and refilling. The Fail sound plays the moment the tank runs dry
* No restrictions on when it can be used (decided 2026-09-15): in the mine, in the camp, during combat, at night. The fuel limit is the only guard against abuse; if a hop over the wall turns out to be a problem in play, the fix is tuning fuel, not adding rules. The mine’s bedrock and the map’s own edges are the only bounds. There is no fall damage (decided 2026-10-05, see "Health and Revives"), so the cut-out height is no longer a limit
* Server authority follows the tools rule: the client asks to start and stop burning, the server owns the fuel and refuses a start on an empty or locked tank; the owning client applies the lift itself (it owns its character's physics) from the replicated burning flag. Every player sees the pack on the character’s back (GameAssets/Wearables/JET_PACK) with a flame and light while it burns, and hears the burn as a 3D loop on that character. Store prices for levels 2 to 5: 20 / 50 / 120 / 300 Gold (placeholders)
Posts
* Posts are the primary defense weapon: more powerful than every other weapon, and each needs a player to operate it
* There are multiple Post Types. Players pick theirs before a run through the Post loadout slot (one only); every new player starts with the Machine Gun unlocked and equipped. The lobby store for posts is a later milestone, so until then the slot is empty and every claim spawns the Machine Gun (an admin dev tool picks the other type for testing)
* As built (M25): two Post Types, Machine Gun and Rocket Launcher, models under ReplicatedStorage.GameAssets.PostWeapons named by their enum key. Neither has ammo or a reload (decided 2026-09-18): the fire rate is the only limit on a held trigger. The Machine Gun is hitscan. The Rocket Launcher fires a rocket (decided 2026-09-18): the server flies it in a straight line at 120 studs per second, cast segment by segment against the world and the enemies, and where it first lands everything within 12 studs of the impact takes the weapon's damage; past its range it bursts in the air. Every client flies the GameAssets/Projectiles Rocket model from the launch message, with the smoke trail authored under its TailAttachment (any ParticleEmitter there is the trail; a bare attachment gets a placeholder) and a 3D flight loop riding it, and bursts it where the server says with the authored GameAssets/Effects/RocketBlast effect (each emitter fires its BurstCount once, lights flash briefly; a missing template gets a placeholder fireball) and the explosion sound. Three sounds: Post_RocketLauncher_Fire at the launcher, Post_RocketLauncher_Flight on the rocket, Post_RocketLauncher_Explode at the impact; the gunner also hears the hit confirm when the burst hurt something
Post Types
* Decided 2026-10-15 (with Classes): a Post Weapon is carried by a class, never picked on its own, and every class has a post of its own; the Recruit's Machine Gun is the one post nobody buys. The roster below is the twelve launch posts (each described in full on its class under "Classes") and a bank for later classes. Every post keeps the shared rules above (rotating base, turn speed, pitch range, Iron upgrades at the Post Upgrade Table, a reticle, a fire sound and a hit confirm)
* Machine Gun (built, M25; Recruit): sustained fire with overheat
* Rocket Launcher (built, M25; the Pyro's since 2026-10-20, the Demolitionist's from 2026-10-15 until then): one rocket on a reload, big splash at the point of impact. The burst post; it owns "hit a group hard at a spot you aim"
* Minigun (Gunner): spins up for a second (fixed; no upgrade shortens it, so letting go to re-aim always costs the spin-up), then a stream with more damage per second than the Machine Gun, half again the heat budget (6 s of fire to the Machine Gun's 4, decided 2026-10-19 after the first Gunner playtest: a burst weapon, not a sprinkler), slower turn. Its status bar shows heat like the Machine Gun's; the spin-up is heard, not drawn
* Railgun (Sniper): hold to charge (4 s to full; Fire Rate shortens it), release to fire a shot that goes through two bodies in a line (one under half charge) for the square of the charge reached, so a snap shot is a sliver and a held one the full 260; no reload, the charge is the pace (2026-10-19). Aimed through the Sniper Rifle's scope glass and zoom, the shot converging on the reticle. Headshots are the Railgun's alone (decided 2026-10-19): a hit in the top 30% of a target's box does 3x and the shooter alone sees a HEADSHOT BONUS callout rise off the body; no other post or hand weapon has one. Its fourth upgrade is Headshot, a quarter more per level to 4x at level 4, in place of Range (600 studs already reaches past every spawn), and Damage levels no longer add pierce bodies (a maxed gun through seven heads was the Saw Gun's lane with the Sniper's damage). The first hold-to-fire post
* TNT Launcher (Demolitionist; the Napalm Mortar, the Pyro's, until 2026-10-20, when the two classes swapped posts: a lob is a timing weapon however clean, and the combat class should have the direct one): lobs a TNT bomb that bursts into a pool of fire where it lands and burns for several seconds, stacking on what stays in it. The shell climbs at a fixed 60 degrees and the launch speed is solved per shot so it falls on the point the reticle aims at, up to the gun's reach, with a ring on the ground where it will land (2026-10-20): the gunner reads the marker and the skill is the timing, not guessing the arc. It aims steeply enough to drop a shell at the post's own feet. Its four rows are Impact Radius (the burst and the pool), Fire Damage (the burst and the pool's burn), Turn Speed, and Fire Length (the pool and each burn stack), decided 2026-10-20 in place of Damage, Fire Rate, and Range: a faster reload would let pools overlap and restack their burns, and the arc already reaches past the wall. Burst damage 100 and a pool that burns 18 a second (decided 2026-10-23; 48 and 12 before, a fifth under the Pyro's Rocket): 20 a second per body on the burst, under the Rocket, and about 42 on a body that stands in the fire for the pool's whole life, the condition the Rocket never needs; the mining classes' posts aim at 15% under the Recruit's on one body and earn the rest on a group. It fires and bursts with the grenade launcher's sounds. The pool, like a burning monster, is Roblox's own Fire (2026-10-20)
* AA Launcher (Air Defense): lock-on missiles, up to three locks at once, bursting near flyers; no lock on ground monsters, where a missile dumb-fires with a small splash weaker than a Rocket. Worth a class only if flyers come in flocks, so it and the Air Raid Contract are one decision
* Auto Machine Gun (Ranger; 2026-10-16, replacing the Grenade Launcher): an unmanned machine gun that targets like a tower and fires all night, so its owner fights on foot. Ranger pass, 2026-10-19: half the Machine Gun's shot (6) in 3 s bursts with 4 s cooling, about a third of a manned Machine Gun sustained (60% damage with the Machine Gun's heat was worth more than the Gunner at the Minigun once its aim was fixed); it aims its pitch from its muzzle, not its base, so a monster right below the post is hit
* Mine Layer (Engineer; 2026-10-16, replacing the Salvage Gun): lobs proximity mines onto the path that arm where they land and blow when stepped on; up to a dozen armed at once, all fizzling at dawn
* Tesla Arc (Electrician): a sustained arc that jumps from the target to the nearest other monsters, so its damage rises with how tightly they bunch and it never needs aiming at a group. Worse than the Rocket Launcher on one big monster, better at a jammed gate
* Fault Line Drill (Prospector; built 2026-10-22, replacing the Salvage Gun, which had moved from the Engineer on 2026-10-16): fires a drill bit at the reticle, and where it lands a crack of rock spikes races on along the ground for 100 studs, hurting every monster on the line and knocking it flat; the crowd-control post, and the one post that shapes the ground. See the Prospector under "Classes"
* Saw Gun (Hauler; 2026-10-16, replacing the Catapult): launches a spinning saw blade in a line that cuts through every monster it meets for full damage until its range runs out; slow fire, best down a packed lane
* Magnet Gun (Medic): no damage. Fire at a spot and every monster within a radius is pulled toward that spot for a few seconds. Pulling toward the aim point, not the post, is the design: onto the Pyro's Remote Charge, off the gate, into the Saw Gun's line
* Bank for later classes: Laser (a continuous beam whose damage climbs the longer it stays on one target; the Prospector's first draft, dropped because it felt like a thinner Minigun), Pressure Cannon (a water jet that pushes monsters back and knocks small ones over, modest damage, a post that buys time, and by day strips filler rock from the mine face; the Prospector's until 2026-10-16), Catapult (lobs a boulder in an arc for heavy damage and a knockdown where it lands, then it rolls on down the slope; the Hauler's until 2026-10-16; the Blades post took its place as the Saw Gun), Light (a beam that slows what it touches and deals a little damage), Land Mine (lobs mines that arm where they land), Cryo Cannon (a cone that builds frost, freezes solid once full, and the frozen monster shatters for bonus damage; only if the payoff is visible, prototype the shatter first)
* Cut (2026-10-15): Mortar as a post (same job as the Rocket Launcher; it lives on as the Engineer's Mortar Tower), Harpoon (needs drag physics and a reason to drag), Net Launcher (hard to read), Searchlight (a post you stand at has to shoot), Ore Cannon (replaced by the Drill Rig tower), Flak Cannon with a manual detonate (the lock-on AA Launcher took its place)
Claiming a Post
* Every map has 6 posts along the defensive wall; every post starts Unclaimed. The sign on each shows its number and status: UNCLAIMED, centred on the sign, until somebody claims it, then the owner's headshot, display name, and Post Type. The prompt hangs 3 studs below the sign's centre so it never covers the text
* A "Claim Post" proximity prompt on the sign (1 second hold) shows only to players who have no post yet, on posts nobody owns. Triggering it gives ownership. Claiming is free (decided 2026-09-25: a post is every player's guaranteed role and the choice is where, not whether, so the old 10 Gold was only friction before the first night; CLAIM_PRICE_GOLD stays as the knob for the day posts become unequal, and a price above 0 would need its sign line back)
* The owner's Post Weapon is cloned onto the post's Spawn part (the weapon's own base is the same cylinder). Only the owner can use the weapon. The per-post upgrade bench is gone (2026-10-01): upgrades are bought at the Post Upgrade Table in the defense building
* A claim lasts the run: it ends only when the player leaves (the weapon goes, the sign reads Unclaimed again). Their upgrades go with them
Using a Post Weapon
* Every Post Weapon has a "Use" prompt on its Prompt part (the designer's invisible part; it sat on CharacterSpawn until 2026-10-09), shown only to the owner while on foot; the Post Upgrade Table's display weapon strips it. Triggering it enters Post Weapon Mode: the character is placed on CharacterSpawn with hands on HandleLeft and HandleRight (IK), the held tool is put away, the balances, backpack, jet pack, and tool bar HUD are hidden (decided 2026-09-18), the camera moves to the weapon's CameraLocation looking down the barrel with the weapon's own field of view (an FPS view near the end of the muzzle), and the reticle shows
* Fire: Left Click (PC), RT (gamepad), or press/hold the Fire button (touch); holding fires on the weapon's interval. Exit: Spacebar (PC), A on Xbox or Cross on PlayStation (B also works), or the touch Exit button, which takes the place of the jump button while mounted since there is no jumping at a gun (decided 2026-09-18). Keyboard and gamepad see a white hint near the bottom of the screen naming their key; touch sees the button instead. Opening any menu also exits. On exit the camera returns to normal
* Each weapon type has its own reticle image (shared Icons, POST_WEAPON_RETICLE): both launch types have theirs; a type without one shows the mining dot
* Machine Gun overheat (decided 2026-09-18): holding the trigger builds heat, full after 3 seconds of fire (cut from 5 in play, 2026-09-18); heat only cools once the trigger rests, taking 3 seconds from full. An overheated gun refuses to fire until fully cool; the Fail sound plays the moment it overheats and on each fresh trigger pull while locked. A bar just above the exit hint fills with the heat, green when cool shading to red when hot, with OVERHEATED above it while locked (GameData HEAT block)
* Rocket Launcher reload (decided 2026-09-18): one rocket every 6 seconds; the reload is the launcher's fire rate, so Fire Rate upgrades shorten it (6 / 5 / 4.3 / 3.75 / 3.3 seconds; decided 2026-09-18). The same bar shows it: full and green when loaded, empty and filling red while reloading with RELOADING above it, green again when done (GameData RELOAD_SEC)
* The gunner hears the machinery whir while they turn or tilt their post weapon (Post_Turn, a 2D loop for the gunner only that fades in as the aim starts moving and fades out when it stops), so the slow view reads as the machine moving rather than sluggish controls (decided 2026-09-18)
* Sounds: each post weapon has a fire sound (3D from the muzzle, one clip per shot; a short clip with no tail, since Fire Rate upgrades stack them) and a hit confirm for the gunner, AudioPlayers under SoundService.Sfx named Post_<Weapon>_<Action> (decided 2026-09-18)
Aiming a Post Weapon
* Weapons sit on a rotating base (the Spawn cylinder) that turns 360 degrees. Left and right is the base turning, no faster than the weapon's Turn Speed; up and down is the gun tilting freely within the weapon's pitch range. Both weapons look down to -70 degrees (2026-09-30, from -40 and -35: the gun sits a dozen studs up, so the foot of its own tower needs a steep look) and straight up to 89 degrees (2026-10-06, from 45 and 60: Flyers hovered over a post the gunner could not raise to). The gunner and the weapon visibly turn with the base
* Server authority follows the weapons rule: the client sends its yaw and pitch a few times a second, the server refuses any turn the base could not have made at its turn speed and echoes the accepted aim on the weapon model, and every client turns and tilts the weapon from that. A shot is a request carrying the muzzle ray; the server checks the gunner, the fire cooldown, and that the ray starts at the muzzle it computes itself, then decides the hit exactly like a handheld weapon
Post Weapon Upgrades
* Every Post Weapon can be upgraded. Every attribute can be upgraded 4 times, each upgrade costing progressively more Iron Bars (10 / 40 / 120 / 300 since M63, 2026-10-11, when post rungs moved from Gold to Iron: day 1 refines no Iron by design, so night 1 is fought on bare posts and the first rung is a day-2 buy from one day's Iron, the rest climbing with the fortification ladder; 15 / 90 / 270 / 800 Gold from 2026-09-29, a cheap first rung then the Pick Axe's ladder; 15 / 30 / 60 / 120 before that maxed three attributes by day 7). Upgrades are never gated (upgrade N needed Camp Level N until 2026-09-28; the Camp Level was removed on 2026-10-06). The Machine Gun is the yardstick for player damage (12 damage since 2026-09-29, 4 s of fire before the overheat, about 69 DPS sustained and 120 while firing against the rifle's 55; 15 damage for a day before that made every enemy feel easy; the Rocket Launcher 200 a shot; 2026-09-28). Each Post Weapon lists its own four upgrades in GameData/Posts/PostWeapons (decided 2026-09-29): the Machine Gun has Damage (HP deducted from enemies hit), Fire Rate (how often a round fires), Turn Speed (how fast the base rotates), and Cooldown (how fast an overheated gun cools; its 350-stud Range never needed upgrading); the Rocket Launcher has Damage, Fire Rate, Turn Speed, and Range (how far a rocket flies before bursting). Each upgrade adds a share of the base stat (Damage +25%, Fire Rate +20%, Turn Speed +50%, Range +20%; Cooldown is the one attribute that steps rather than compounds, taking a sixth of the base cool time off per level so every rung is worth the same half second and the Machine Gun cools from full in 3 / 2.5 / 2 / 1.5 / 1 seconds, decided 2026-09-29). The Upgrade menu shows only the rows the weapon offers, and the server refuses an upgrade the weapon does not have. Bases start slow (Machine Gun 22 degrees per second, Rocket Launcher 12; cut to a quarter of the first numbers in play on 2026-09-18) so the Turn Speed upgrades are felt. The gun tilts up and down at the same rate as the base turns (decided 2026-09-18), so every direction feels equally heavy
Upgrading a Post Weapon
* The Post Upgrade Table in the defense building (Camp.DefenseStore.Tables.PostUpgradeTable; decided 2026-10-01, replacing the per-post bench) carries a "Post & Gadget Upgrades" prompt (renamed from "Upgrade Post" on 2026-10-19, when the class gadget's upgrades joined it) anyone can trigger and it opens the Upgrade menu for everyone (2026-10-06; until then a player without a post was told to claim one first). Upgrades belong to the player, not the post: before a claim they are bought against the loadout post weapon the claim would spawn, and a claimed post fires with every upgrade already bought. The table also shows a small display post (the designer's DisplayPost model sets its spot and size) that each client redraws as the current fortification tier's post with that player's own loadout post weapon on top, no sign, no prompts, display only. The Upgrade menu: each attribute in a row with 4 empty squares beside it and an Upgrade button showing the Iron Bar icon and the cost (the Gold Bar icon until M63). Tapping the button buys the upgrade if the player has the Iron Bars, and the next square fills in (square 1 = 1st upgrade and so on). Without enough Iron the player is told with the Fail sound; a locked upgrade shows CAMP LEVEL N REQUIRED in red under its squares with a greyed button, and tapping it plays the Fail sound and repeats the requirement in the feedback box; a maxed attribute reads MAX. Under the post's rows, a class whose gadget scales (the Auto Turret and the Remote Charge; never a utility gadget, and never one whose job is the same on night 1 and night 10, so the Flare lost its rows on 2026-10-21: only a gadget that must keep pace with the waves or the mine gets upgrades) sees a second heading, "Upgrade Auto Turret", and one more row of the same shape for the gadget: one level like a Tower's, its squares the levels bought, its button the next Iron price, every number in the gadget's stats table moving a step (M67, 2026-10-19). The rows shrink to fit while the gadget block shows
Defenses
* Defenses are automated defense units, called Towers, that players place in a defined area in front of the camp, outside the walls
* Towers work like traditional tower defense units, damaging and slowing enemies as they work their way to the camp
* After placing a Tower, its owner can upgrade it up to 4 times
* It costs Iron Bars to build and upgrade Towers
* Towers are unlocked and equipped in the lobby via the loadout
* Every Tower has HP and can be attacked by some enemies. Losing all HP destroys and despawns it
* The camp has a limit of 12 active Towers, shared out evenly among the crew sampled at dawn (MAX_ACTIVE_TOWERS_CAMP in GameData/Defenses/Towers, PlacementRules.towerAllowance is ceil(camp / crew), so a solo player builds the whole camp's worth and a crew of six two each; a leaver's share opens the next morning; decided 2026-09-28, replacing 5 per player). Build prices 20 to 45 Iron and upgrades 10 / 20 / 40 / 80 and up (two thirds of the 2026-09-25 prices). Prices (GameData/Defenses/Towers) follow the balance plan's tower economy: a day's Iron buys about one new Tower or one meaningful upgrade, never both. Every build and upgrade price tripled on 2026-10-06 (Sentry Gun 60 Iron to build, 30 / 60 / 120 / 240 to upgrade, the other kinds in step; the Sentry Gun's build came down to 50 and the buildable wall segment from 12 to 10 Iron on 2026-10-23) after the second M34 playtest, where nights 4 to 9 did no wall damage and the cap was full of maxed Towers by night 10
Unlocking Towers
* Decided 2026-10-15 (see "Classes"): Towers are never bought one by one. A class carries exactly one Tower as its class item (one or two until 2026-10-19; every class is one weapon, one post, one tower, one gadget) and a player places only their class's kind in a run; the Drill Rig is a Tower that mines instead of defending (see "Tower Types"). Walls are always buildable and traps are level content open to everyone
Equipping Tower Loadouts
* Gone with Classes (2026-10-15): there is no loadout. The class brought on the run decides the Towers; the earlier 3-slot Loadout Menu was never built. Until every class exists, an admin dev tool fills a test class's slots (as with Posts)
Defensive Zones
* In the gameplay place, players build Towers in pre-defined Defensive Zones
* Some maps have 1 Defensive Zone, others have several
* Defensive Zones are grid based and overlap the Wave Areas, the larger pre-defined grid areas that the monster waves traverse. Where a Wave Area is wider than the Defensive Zone inside it, the strip beside the zone is closed to monsters (shared PathAreaRules, applied when MonsterPathManager builds its grid; decided 2026-09-29): level with the zone along the approach but outside it across, so walls built to the zone's edge cannot be walked round where nothing can be built. The Wave Area beyond the zone, toward the spawns, stays open at its full width. Monsters leave the grid only to chase a player
* Towers cannot be built outside a Defensive Zone and cannot overlap other Towers or Traps
* The two cells nearest a wall, a post, or the gate are kept clear (decided 2026-09-30): a cell whose centre is closer than FORTIFICATION_CLEARANCE_CELLS (2, GameData/Defenses/Placement) cells to a fortification is reserved before anything is built, whatever shape the wall line takes. Every cell on the camp's side of the fortification line is reserved too (2026-10-01): a flood fill from the Refinery across the ground, never stepping under a wall, post, or gate, marks the inside, so a pocket behind an outer wall counts and the zone part may overlap the camp to let the grid hug the walls; a model's bounding box is stood upright first, since a post's pivot lies on its side. The reserved set is mirrored across the zone's centre line (IS_RESERVED_MIRRORED, with the zone part centred on the gate) so the two halves read the same. The server reserves them when it measures the zone and publishes them on the zone part; the Tower Table draws grid lines only along buildable cells, so the grid stops at the walls, and the ghost steps around the rest
* Every Tower and Trap has a grid footprint (cells wide by cells deep) in the same units as the Placement and Wave Areas
* In Repair Mode both the placement grid and the boundaries of every Defensive Zone are visible, so players know the placement constraints
* Authoring: each Defensive Zone is a Part under Camp.DefensiveZones; its size and rotation define the grid, whose cell size lives in GameData/Defenses/Placement (CELL_SIZE_STUDS). The server keeps the occupancy of every area as Lua data; the client draws the grid and outline locally
Building Towers
* As built (decided 2026-09-30, replacing the Defenses tool below): Build Mode starts at the Tower Table, the map table in the defense building (Camp.DefenseStore.Tables.TowerTable, designer-authored; renamed from the Defense Table on 2026-10-01 when every defense menu moved into the building) with a ProximityPrompt. Triggering it puts the player in Build Mode on the server (DefenseTableManager, published privately as IsInBuildMode; PlacementManager refuses a build outside it); the client freezes the character where it stands and eases the camera up into an overhead view of the Defensive Zone over CAMERA_TRANSITION_SEC (1 s) and back down on exit, the character held until it lands (2026-10-02; BuildCameraRules: distance, pitch, pan speed and zoom bounds published as GameMetadata; the view opens at 75 studs and zooms out to 210 since 2026-10-02, 150 and 300 before, for phones), streaming focused on the zone so the placements there load. A classic tower defense screen: the BuildBar along the bottom lists every Tower the loadout brought and every Trap with its Iron price, greyed while it cannot be paid for; a tap or its number key brings out that item's ghost, a second tap puts it away; a tap or drag on the grid moves the ghost snapped to the cells, red where it cannot stand, with the PlacePanel floating beside it, to its right or to its left near the screen's edge so it never covers the ghost (2026-10-02): Place with the price, green while the ghost can go down and be paid for and red otherwise, Rotate (a quarter turn each tap, or R), and a red Cancel; every standing Tower shows its range ring at its level while the mode is on; after a build the ghost steps to the nearest free spot beside the one it filled; with no ghost out, tapping one of the player's own Towers opens the Tower Menu and one of their Traps floats the SellPanel, both offering Move, which picks the placement up as a ghost (TryMovePlacement); dragging elsewhere pans (as do WASD and the arrows), the wheel or a pinch zooms, and Exit asks the server to end the mode. Build Mode also ends when the player is hurt, dies, or leaves, and the camp streams back in around the character before the camera returns. Every tap lands on BuildSurface, one invisible full-screen Modal button that frees the locked first-person mouse. The tool bar and the Defenses tool no longer play any part
* History (superseded 2026-09-30): players equipped the Defenses tool from the tool bar (decided 2026-09-21, replacing the Hammer: in first person the cursor is locked, so a bar that needs clicking cannot work). Equipping it is Build Mode: the tool bar slides away and the Defense loadout takes its place at the bottom of the screen, alongside every Trap the player currently owns, each entry numbered like a tool slot, and the first entry is selected at once (decided 2026-09-21). The Defensive Zones (grid and boundaries) appear on the map at the same time
* Each entry is a square slot styled like the tool bar's (decided 2026-09-21, replacing the circle): the item's picture inside, a small Tower or Trap badge in its top-left corner, the number key top-right, the name above the slot, and the Iron price (or the count of Traps carried) under it. With enough currency the entry is full colour; without it, the entry is slightly greyed. The selected slot carries the tool bar's accent stroke
* Pressing an entry's number key (or tapping it on touch) selects that Tower: a 3D preview stands 20 studs in front of the player (doubled from 10 in play, 2026-09-21), snapped to the grid as they move, but only while that spot is inside a Defensive Zone (decided 2026-09-21: a preview far away could place something the player cannot see). Out of the zone the preview is hidden and the hint reads "Go to the Defensive Zone to place Defenses"; inside it keeps its own colours where it can be built and every part goes red where it cannot (a highlight tint did not read through the translucent preview) with the hint reading "Cannot place here"; where it can, the hint names the keys. Pressing another number swaps the preview; one entry is always selected while Build Mode is on, and it stays selected after a build (decided 2026-09-21). Every zone floats an always-on-top "DEFENSIVE ZONE" sign while Build Mode is on
* Building is a left click (PC), RT or R2 (gamepad), the action button (touch), or the Build button that shows BUILD and the price while the preview is green. A right click (PC) or B / Circle (gamepad) leaves Build Mode (the Defenses tool unequips). Touch sees the Build button; keyboard and gamepad see a white hint ("LMB to place, RMB to exit"; "RT to place, B to exit") instead, since a locked cursor cannot tap a button (decided 2026-09-21). An "EXIT BUILD MODE" button stays up the whole time Build Mode is on, tapped on touch and showing its shortcut ([RMB] or [B]) for everyone else. Building on a taken cell says "Not enough space". A counter at the left end of the bar shows a Tower icon and "placed / limit" (red once the limit is reached), so the 5-Tower limit is never a surprise
* Building places the Tower and deducts the currency, playing PlacementBuild and the SaleSuccess ring together (2026-10-09; moving a placed Tower or Trap plays PlacementBuild alone, since nothing is charged). With too little currency the preview still turns green, but the price reads in red, and building gives "You don't have enough Iron Bars" in the feedback box with the Fail sound
* A successful build spawns the Tower at the chosen cells and it becomes active
* Every active Tower carries a BillboardGui showing its name, its HP bar, and the display name of its owner
* As built (M26): the BuildBar ScreenGui (scripts/studio/build_build_bar_gui.luau) holds the entries and the Placement panel; the Defensive Zone grid is drawn as thin lines on the part's top face with a box around it, client-side only. A placement turns in quarter turns since 2026-10-02 (the Rotate button or R; the turn travels with the build or move request, the shadow carries PlacementRotation, the footprint swaps columns and rows on odd turns and the client turns the model; until then a preview had no rotation, decided 2026-09-21): a footprint's columns run along the area's X axis and its rows along its Z. Every footprint is whole units of 2 cells and every grid's column and row counts are rounded down to even (PlacementRules.FOOTPRINT_UNIT_CELLS, the server warning on an odd footprint at startup), so the smallest placement tiles any grid (decided 2026-10-02). Building exits Build Mode; tap the entry again for another. Tower placeholder prices: Sentry Gun 30, Flamethrower 45, AA Turret 53, Frost Tower 45, Tesla Coil 60, Sniper Tower 68 Iron (raised 50% on 2026-09-25 after a solo playtest, halves rounded up), upgrades 15 / 30 / 60 / 120 (Tesla and Sniper 25 / 50 / 100 / 200), all in GameData/Defenses/Towers. A Tower whose builder leaves keeps standing under their name; nobody can sell or upgrade it
* Server authority follows the tools rule: the client asks to build at a cell with a facing; the server checks Repair Mode, the loadout, the Tower limit, the cells, and the balance before spawning. Towers are Lua state with one shadow part each, rendered by the clients from the ReplicatedStorage template
Upgrading and Selling Towers
* A placed Tower has an "Upgrade/Sell" proximity prompt, visible only to its owner
* Activating it opens the Tower Menu, in the tower defense format:
   * Left upper panel: an image of the Tower with its name and current level
   * Left middle: a Target Priority toggle. A "TARGET PRIORITY" header over the current selection ("Closest" by default), with arrows on each side that cycle through Closest, Furthest, Strongest, Weakest. The Tower targets enemies in range by the chosen priority
   * Under it, a Stats panel listing the Tower's four stats. Which four depends on the kind (see "Tower Types"; M27), so a Frost Tower never shows a Damage of 0
   * Left lower: a red Sell button showing the sell value (50% of everything spent on the Tower). Pressing it adds the value to the owner's Iron balance, despawns the Tower, and closes the menu
   * Right upper: an Upgrade button with 4 empty circles under it. The button names the upgrade (Level 2 and so on) and its price. Pressing it with enough Iron upgrades the Tower, refreshes the menu, and fills the next circle; without enough Iron the player is told with the Fail sound
   * Right lower: an Upgrade Stats panel with an icon for each stat the upgrade changes, its current value, and an arrow to the value after the upgrade
Tower Types
* There are multiple Tower types, each with its own visuals and behaviour. Since 2026-10-15 a Tower is reached only through a class that carries it (see "Classes"); each class carries one (the Gunner the Sentry Gun, the Sniper the Sniper Tower; the Recruit, the free class, the Sentry Gun)
* Four new Towers for the launch classes (decided 2026-10-15, each described on its class under "Classes"; the Drill Rig built 2026-10-22, the rest not built): Drill Rig (Prospector: on the defensive grid, drills Iron and Gold into its own stock over time up to a cap, collected through its prompt by anyone, defends nothing, has HP, counts against the cap, so a defensive slot is traded for an income a bad night can wreck), Mortar (Engineer: lobs over the wall at the back of a group), Rock Slide (Hauler: a stacked pile that releases a boulder down its lane every few seconds, knocking down whatever is in the line), Repair Tower (Medic: no gun, slowly repairs every tower and trap in its radius through the night). Each is carried by that class alone
* All Tower stats live in GameData/Defenses/Towers so they are easy to change. Every Tower has 4 upgrade tiers, each raising specific stats
* Like Posts, Tower models live in ReplicatedStorage.GameAssets.Towers, named by their enum key
* Every Tower except the Tesla Coil is a stationary base with a turret on top that turns a full 360 degrees toward its target, like a tank. Each kind lists the four stats the Tower Menu shows and an upgrade may raise; every kind also has HP. Behaviour numbers that are not one of the four (cone angles, tick rates, chain jump distance, stun length) live in the same GameData entry and never change with upgrades (M27, decided 2026-09-22)
* Range is measured from the edge of the Tower's footprint, not its centre (decided 2026-09-22), so the menu's number is how far past the Tower it reaches whatever its size. In Build Mode the preview carries a ring on the ground showing that reach, and every standing Tower shows a fainter ring at its level so the gaps in the coverage are plain (2026-10-02)
* Targeting: a Tower picks one enemy inside its Range by its Target Priority (Closest, Furthest, Strongest, Weakest by current HP), fires only while it has a target, and turns its turret to face it. Ground-only Towers ignore air units and the AA Turret ignores ground units
* Roster (behaviour built in M27):
   * Sentry Gun: the basic default Tower every new player has. Shoots one land enemy at a time. Stats: Fire Rate (time between bullets), Damage (per bullet), HP, Range
   * Flamethrower: a single turret that breathes a flame for a short time, hitting every enemy in a wide cone in front of it, at very short range. Stats: Flame Length (how long each flame lasts; the designer's "fire rate"), Damage (per flame tick), HP, Range. Fixed: the cone angle, the damage tick interval, the rest between flames
   * AA Turret, built as the Missile Turret (2026-10-20): a Sentry Gun that fires at anything, flyers first, so the Air Defense class keeps a tower on a night without them (air only, unable to hit ground, until then). Stats: Fire Rate, Damage, HP, Range
   * Frost Tower: the Flamethrower's shape, but it breathes frost that only slows. Every enemy in the cone is slowed for a while; no damage. Stats: Slow Rate (how much slower a hit enemy moves, as a percentage), Freeze Length (how long the slow lasts), HP, Range. Fixed: the cone angle, the frost pulse interval
   * Tesla Coil: a stationary tower with electric coils, no turret, that zaps 360 degrees around it. Each zap hits the picked enemy and chains to further enemies within a fixed jump distance, damaging each and stunning it briefly. Stats: Damage (per hit, first target and every chained target), Fire Rate (the zap interval; a slow, heavy rhythm), Range (the radius the first target is picked in), Chain Count (how many extra enemies the bolt jumps to: from 1 at level 1 to 4 at level 5). Fixed: the jump distance, the stun length
   * Sniper Tower: far Range and heavy Damage but a very low Fire Rate. Shoots one land enemy at a time. Stats: Fire Rate, Damage, HP, Range
* Towers and Traps fight monsters exactly as they fought the dev tools' walking dummies (M29): monsters are the same kind of target. The dummies stay as a test tool: target dummies that walk a straight line toward the admin, on the ground or in the air, honouring slows and stuns and stopping to attack a barrier in their way
Traps
* Traps are passive defensive placements: barriers, spikes, mines, and the like, used to direct enemy movement or to damage and slow enemies
* Unlike Towers, Traps are consumable and are bought at the Defense Store with Iron Bars
* Players can carry up to 3 different Trap types at once, with no maximum count per type
* Traps are per map (decided 2026-10-12): each map's data lists the Traps its runs offer, and every player in the run can buy all of them, alongside the one Tower their class brings. A Contract tier may add to the map's list later. Until M41 builds the per-map list, every Trap is offered on every map
* Like Towers, Traps can only be placed in a Defensive Zone and use the same grid
* Traps cannot be upgraded
* Every Trap has HP and can be destroyed by enemies. Some Traps despawn on their own after use (a Bear Trap, for example, despawns once triggered)
Buying Traps
* Traps are bought from the Tower Table's Build Mode (2026-09-30); before that the plan was a Defense Store structured like the Mining Supplies Store: a stand per Trap showing its model (the real trap template, shrunk by the DisplayScale attribute the designer sets on the standâs ItemSpawn part, since the templates are grid sized; 2026-09-25), and price, each with a purchase proximity prompt
* With enough Iron the price is deducted and the Trap is added to the player's run inventory; with too little the player is told with the Fail sound
Placing Traps
* Placing a Trap works exactly like building a Tower: the owned Traps appear beside the Defense loadout in Build Mode, with the count owned in place of a price, and placing one consumes it
Selling Traps
* A placed Trap has a proximity prompt visible only to its owner reading "Sell: [price] Iron Bars", a 1 second hold, worth 50% of the purchase price. Activating it adds the value to the owner's Iron balance and despawns the Trap
Trap Types
* Stats and prices live in GameData/Defenses/Traps; models in ReplicatedStorage.GameAssets.Traps, named by their enum key. Placeholder prices: Wall 12, Spike Trap 15, Goo Pit 10, Land Mine 20, Bear Trap 8, Decoy 18 Iron; footprints in the same file. The Wall is a run four cells long and two deep (16 x 8 studs since 2026-10-02, the model filling the whole footprint so a row of walls joins with no gap; 4 x 1 from 2026-09-25, a 2 x 2 block before), laid along the Defensive Zoneâs columns, which run across the monstersâ approach, and turned with the Rotate button like every placement (2026-10-02). The Goo Pit is 4 x 2 and the Land Mine and Bear Trap 2 x 2 since the same day, every footprint being whole units of 2 cells. Every Trap has HP. A Trap that "touches" an enemy means the enemy's footprint overlaps the Trap's cells; air units never touch a Trap (M27, decided 2026-09-22)
* Roster (behaviour built in M27; Tiger Teeth renamed Wall, a clearer concept):
   * Wall: a barrier meant to slow and corral enemies. If there is a path around it, enemies take that path; if there is none, they attack it (the routing is M29; until then a blocked dummy attacks the Wall in front of it). Stats: HP
   * Spike Trap: damages enemies that pass over it. Two states, Down (the default, spikes hidden below the platform) and Up. When an enemy touches it the spikes go Up and damage every unit on top; it stays Up for Up Time, then goes Down and recharges for Recharge Time before it can go Up again. Stats: HP, Damage, Up Time, Recharge Time
   * Goo Pit: a platform of goo that slows every enemy walking on it. Stats: HP, Slowdown Speed (percentage), Slowdown Length (how long the slow lingers after leaving)
   * Land Mine: explodes when an enemy touches it, damaging every unit within its Range, then it is gone (one use). Stats: Damage, Range
   * Bear Trap: triggers on contact, damaging and stunning the one unit that touched it, then it is gone (one use). A stun is a slow of Stun Speed percent for Stun Length; 100% is a full stop. Stats: Damage, Stun Speed (percentage), Stun Length
   * Decoy: a barrier with HP that draws enemies within its Range toward it, if those enemies prioritise attacking players. It carries a "draws attacks" flag that enemy targeting reads at M29. Stats: HP, Range
* Status effects: a slow is a percentage off an enemy's speed for a duration and the strongest active slow wins (they never stack); a stun is a 100% slow; a burn is damage per second for a duration and a fresh burn restarts the clock. All three live on the target itself, so a Tower, a Trap, or later a weapon applies them the same way (M27)
Wall Repair
* Repair works like mining (decided 2026-09-17, replacing a single full-price repair prompt): in Repair Mode every Hammer swing at a damaged structure adds 30 HP and costs the player 1 Iron Bar at fortification level 1, 60 HP for 2 Iron at level 2, and 120 HP for 4 Iron at level 3 (doubling with the wall's HP, decided 2026-09-29, so a full repair is the same number of swings and the same Iron per HP at every level (the chunk tripled on 2026-10-06 after the first M34 playtest spent every Iron and most of each late day on repairs; it was 10 / 20 / 40 HP); a Tower repairs at the level 1 chunk; the swing cost was 4 until 2026-09-25 and 2 until 2026-09-29, when the eighth playtest showed two rebuilt walls a night eating six Sentries' worth of Iron). The last swing pays only for the HP still missing, rounded up. Swings repeat every 0.45 seconds while held, and the Hammer reaches 17 studs, 5 more than the pick axe, because a wall is big
* Every swing is a request the server validates (Hammer equipped, structure damaged, within reach of the structure's bounds, cooldown, enough Iron). A swing that lands plays the hammer sound for everyone nearby. With too little Iron the Hammer does not swing and the player is told once per press
* A destroyed wall or gate is rubble and stays rubble while it is rebuilt swing by swing from zero; its bar reads "Rebuilding n / max". It stands back up only when fully rebuilt (GameData REBUILD_STAND_SHARE = 1, decided 2026-09-17: a wall that reappears after one swing could be flickered in front of the horde for 2 Iron a time). Rebuilding a level 1 wall is 30 swings and 60 Iron
* Repair is never capped
* Towers are repaired exactly like walls (decided 2026-09-22): in Repair Mode a Tower shows the same HP bar and swing price, anyone may swing at it, and each swing adds the same HP for the same Iron. A destroyed Tower is gone, never rubble; it is built again. Traps are consumables and are never repaired
* Fortification level: the gate, all 6 walls, and the look of the posts share one level, 1 to 3 (decided 2026-09-17: a half-wood, half-concrete wall reads as a bug). HP by level: Wall 300 / 600 / 1200, Gate 450 / 900 / 1800 (raised 50% on 2026-09-25 after the five-player test). An upgrade keeps each structure's share of HP rather than healing it, and rubble stays rubble
* The Walls Table in the defense building (Camp.DefenseStore.Tables.WallsTable; decided 2026-10-01, replacing the Workbench just inside the gate) with a floating sign showing "FORTIFICATIONS LEVEL n", a bar of the crew's donated Iron ("pool / required", Iron Bar icon) (the lock line went with the Camp Level on 2026-10-06). The sign is half its old size and hangs on the table's designer-placed Gui part; the small model of the wall line on the table (WallModel) redraws itself as the current tier's walls, posts, and gate on every client. Its proximity prompt, "Contribute 10 Iron" (the number is FORTIFICATION_DONATION_IRON at level 1 and doubles a level, 10 / 20 / 40 since 2026-10-08, so each level takes about the same number of presses as its price climbs; the prompt text follows), moves that much of the player’s Iron Bars into the shared pool per press, ringing SaleSuccess (2026-10-09; CoinsAdded before); no Hammer needed. When the pool reaches the price (150 Iron for level 2, 400 for level 3, solo; a crew pays that times its wave multiplier, 1.6x for two up to 2.8x for six, rounded up to whole donations and recounted each dawn with the crew, since the pool is the one camp-wide Iron sink and repair swings already scale with the number of hammers; decided 2026-09-29) the fortifications upgrade by themselves, and every player gets the CampLevelUp sound and "Fortifications upgraded to level n" in the blue announcement box. Level N needs Camp Level N, and donations are refused while locked so nobody's Iron is stranded in a pool that cannot complete
* The Refinery is repaired with the Hammer like a wall but never bought: its HP and its model follow the fortification level with the walls and the gate (the model since 2026-10-09: GameAssets/Structures REFINERY_1 to REFINERY_3 stand where the map's Refinery is, that model being only a pivot marker like a Wall model, swapped at run start and on every upgrade, with no rubble since its fall ends the run; HP 1000 / 2000 / 4000, doubling a level as they do; decided 2026-09-29, when Camp Level left the game; until then its level was the Camp Level at 1000 / 1500 / 2200 / 3000). Refinery destroyed is the loss condition hook for the run state machine (M28)
* All numbers live in GameData/Camp/Structures and GameData/Camp/Level; placeholders until enemies exist to tune against
Defense design notes (2026-09-16, source for M23 to M27; sections above are updated as each lands)
* S9 — Manned posts (4). Limit 1–2 each. Never auto-fire. The only heavy damage in the game
   * Gatling: balanced generalist, sustained fire. Weakness: never excellent, poor vs Brute/Titan
   * Cannon: heavy single target. Weakness: slow reload, useless vs swarms
   * Mortar: arcing, large blast radius, reaches canyon mouth. Weakness: minimum range, no air
   * Flak Cannon: airburst, hits Flyer groups. Weakness: cannot hit ground
   * Upgrade structure: 4 stat lines (damage, rate, range, one specific), 4 tiers each; tier 1 is the base post. Then one exclusive branch fork with a capstone, paid with gold (it was to be gated at Camp Level 4 before the Camp Level was removed, 2026-10-06)
   * Claiming: one player owns a post — their type, their money, their upgrades. Free to leave mid-fight. Claims release on disconnect, post retains built tier
   * Launch unlocked: Gatling, Cannon
* S10 — Auto turrets (6). Cheap, weak, numerous. Limit 4–8 each. Loadout: pick 3 from the unlocked roster in the lobby, locked for the run
   * Sentry Gun: single target, steady. Workhorse
   * Flamethrower: short range, wide cone, burn DoT
   * AA Turret (the Missile Turret): flyers first, ground too since 2026-10-20
   * Frost Tower: radius slow, occasional freeze. No damage
   * Tesla Coil: chain lightning, brief stun
   * Sniper Tower: long range, high damage, slow. Answers Launchers
   * Tuning rule (non-negotiable): a full turret field holds night 4 and is overrun by night 8. Turrets buy time and cover flanks. They never win
   * Launch unlocked: Sentry, Flamethrower
* S11 — Placements (6). Bought freely in-run at the Defense Building. No loadout — all available always. Reactive, not committed
   * Tiger Teeth: barrier (HP). Blocks movement, enemies attack it

Wave Cycle
* A run is a loop of Day and Night (GDD "Gameplay Loop"; built in M28, decided 2026-09-22). The run state is one of Day, Night, Won, or Lost, held by the gameplay server (RunCycleManager) and published to every client with the day number and the time the current phase ends, so every screen shows the same clock from server time
* A run loads in the morning look with the clock still (the Waiting state) and day 1 begins PRE_DAY_SEC (10 s) after the helicopter leaves, which is when everyone the lobby sent is Ready or the arrival timeout has given up on the missing (decided 2026-09-22)
* Day lasts 320 seconds (GameData/Control/RunCycle DAY_SEC; 5 minutes until 2026-09-29, when 20 seconds were added to the sunset so a crew has time to set up defenses). The gate stands open, players mine, refine, build, and place defenses
* Dusk is the last stretch of the day (RunCycleRules.duskSecForDay: 60 s on day 1 and 5 s more each day to a cap of 90, since 2026-10-02, DUSK_START_SEC / DUSK_STEP_SEC / DUSK_MAX_SEC; a fixed 80 s from 2026-10-01, out of the same 320 s day; the final 60 s from 2026-09-29, 40 s before that, and the final 20% until 2026-09-25): nothing changes in play, only the clock icon turns to dusk, the label under the clock reads SUNSET N instead of DAY N (2026-09-29), and the dusk song starts, so a crew heads home in time. The song fades out over DUSK_SONG_FADE_SEC (10 s) from DUSK_SONG_FADE_LEAD_SEC (5 s) before night falls, so it is silent 5 s into the night (2026-10-02). Dev tool: Pause the run (RunPauseManager, 2026-10-02) holds the clock, the monsters, the waves, Towers, Traps, status effects, and the rescue where they are and moves every deadline on by the pause when it lifts, the clients' clocks holding at the paused moment; players themselves keep moving, so a tester called away mid-run can come back to it The There is no Start Night button: one was added on 2026-10-07 (a crew vote in the day's last 30 s to skip to night) and removed on 2026-10-08 by the designer, who did not like it; the day runs its full length. The count shows on the button (START NIGHT 1 / 3), a pressed button greys, votes clear at dawn, and a player who leaves or dies drops out of the count (StartNightManager, ClientStartNightManager, TryStartNight).. The dusk song starts silent and eases up to its authored volume over 5 s (2026-10-21). Dev tool: Skip to sunset (2026-10-21) jumps the clock to SKIP_TO_SUNSET_LEAD_SEC (5 s) before dusk begins and lets the day run at its normal pace from there, the day keeping its full length (a first cut compressed the rest of the day into the lead, which raced the sun) The night has its own loop, Music.NightSong (authored at 0.5; designer, 2026-10-21): it eases in over 3 s as night falls and out over 1 s at the night's end, following the server's IsNight flag, so it plays through a rescue too.
* Night begins when the day clock runs out. The gate shuts, the night's wave spawns (GDD "Creating Waves"), and the night lasts until every group has spawned and every monster is dead, at which point the next day begins (M29). NIGHT_PLACEHOLDER_SEC (GameData/Control/RunCycle) is 0; above 0 it also ends a night that long after the 90 second spawn window, as a test switch
* The day counter starts at 1 and each dawn adds one; the night’s wave is generated from it (Creating Waves, M30)
* The sky: every map has four looks, day start, day end, night start, and night end (shared LightingPresets, keyed by map, read from Studio and ported by hand; decided 2026-09-22). Day start is set outright when the run loads. Over a day the sky blends steadily from day start (8:00) to day end (18:00 since 2026-10-21, 17:30 before; the same colours); the night opens with a LIGHTING_DUSK_TRANSITION_SEC (1 s) blend to night start (19:12, the light off, just past the engine's sun-to-moon handover, which cannot be blended), then blends night start into night end (20:00, the moon at full) over the 90 s spawn window and holds night end until the wave is done. A cleared night blends night end back to day start over LIGHTING_DAWN_TRANSITION_SEC (1 s) and only then does the day clock start. A DayNightNumber card ("DAY  N" / "NIGHT  N") shows for 3 s once each blend ends, with the DayCard sting on a day (the Rooster crowing first from day 2, the card 3 s after it) and the NightBell on a night; day 1 has its card too since 2026-10-21. Every day, as dusk begins (DUSK_SEC, 40 s before the night falls), every client starts the 2D track Music.DuskSong1 from the top (the track is 52 s, so it runs on into the night; decided 2026-09-25); a day the dev tool cuts short starts it as soon as the lead is reached. Lighting.ClockTime blends the same way between each look's hour, always turning forward round the clock Night dressing (designer, 2026-10-21, all client-side off the run clock): the map's lights tagged NightLight rise to a brightness of 1 and its NightLightBulb meshes turn solid over the day's last 30 s, out over 0.5 s at dawn; the SunRays effect rises from the preset's 0.15 intensity and 0 spread to 0.25 and 0.6 over the day's last 25 s and is the preset's again the moment night starts (laid over the preset through the run cycle manager's sky-applied hook, since the presets write every frame); the map's Moon model (Camp.Moon, its MoonStart and MoonEnd markers in a Markers model so streaming keeps them) climbs from MoonStart to MoonEnd over the night's first 30 s and comes down over the dawn blend from wherever it is; the engine's own moon is hidden (MoonAngularSize 0) and the presets' GeographicLatitude is 23 (27 before).
* Every dawn, and at the first day, the server logs the day, the crew size, and the multipliers to the Output, in the words of "Adjusting for Different Player Counts"; the line no longer shows in the announcement box (2026-09-25), the DayNightNumber card and the clock carry the beat. The card (as built 2026-10-21; day 1 had none before): DAY 1 shows as the first day's clock starts with the DayCard sting (2D); from day 2 the Rooster crows as the clock starts and the card with its sting follows 3 s later; the NIGHT N card shows with the NightBell after the dusk blend
* The run ends as Lost when the Refinery is destroyed or every player is dead with nobody revived in time (see "Health and Revives"). The clock stops and the gate stays as it is. The Refinery falling plays the Game Over screen for everyone ("THE REFINERY HAS BEEN DESTROYED", the camera circling the Refinery), buries everyone still standing in the Cemetery, and ends on each player's grave with the Results Menu reading "RUN LOST" and a Return to Lobby button, which teleports the player to the lobby (built in M32; the end-of-run summary and its rewards are M33). A won run shows the Results Menu as "RUN WON" with the same button. Won is the rescue helicopter leaving with the crew aboard (see Gameplay Loop; M31): the Rescue state sits between, night rules in force, the phase end being the landing time and then the boarding deadline
* Day clock: a bar top centre of the screen (the DayClock ScreenGui). A circle on its left cycles through three pictures, Day, Dusk, and Night; the bar starts full at dawn and empties from right to left until night, so players always know how long they have; "Day N" reads under the bar. At dusk (M33, 2026-10-06) the clock slides up off the top of the screen and the Refinery HP bar (the RefineryHp ScreenGui) slides down into its place: the same box, with the compass home icon on a black square where the clock's circle was (the square flashes red every second while the Refinery is under attack, and the RefineryUnderAttack siren plays once with every flash so the sound lines up with the colour; before M33 the siren looped), a bar filled with the Refinery's HP share in the HP colours, green to red, and "REFINERY HP" under it, so the crew always knows how the thing that loses the run is holding up wherever they are. At dawn the bar goes up first and the clock comes back down after it; each slide takes 0.9 s so the swap is seen
* Camp Map (M33, 2026-10-06): a square panel top right of the screen, its top level with the top of the Refinery HP bar's track (the CampMap ScreenGui; its side is 0.285 of the screen height, so it is the same square at every aspect) that slides in from the right edge as night falls and out again at dawn, drawing the camp from above, zoomed in so the walls and the Refinery fill the square to within a 4% margin. It is fixed north-up with the top toward the gate, where the monsters come from. Every wall, the gate, and the Refinery is drawn from its structure shadow's box, coloured by its health: white at full, yellow down to just over 60%, orange down to just over 30%, red while anything is left, and black with a red X over it once rubble (a thin wall is drawn no thinner than a readable stripe). Each crewmate is a dot in their compass colour, the player looking at the map ringed in white, and every monster the client is drawing is a smaller red dot, so the crew can see which walls are weak, where everyone stands, and where the night is coming from. The structures redraw as their HP changes and the dots move ten times a second; a dot past the edge of the square is not drawn. It hides with the rest of the HUD while a player is dead. The backpack and jet pack stack on the right edge sits level with the balance rows on the left, under the map
Setting Up Waves
Wave Area
* Just like the Defensive Zones, the area that enemies are confined to is a predefined grid that fits the Defensive Zones inside of it
* This ensures that enemies can’t sidestep any towers or traps and that their lanes are clearly defined
* It follows the same format as the Defensive Zones: each Wave Area is a Part under Camp.WaveAreas whose size and rotation define the grid, in the same cell size (GameData/Defenses/Placement CELL_SIZE_STUDS)
* Enemies always stay within the grid unless:
   * A player is within the enemy’s DetectionRange and outside the Wave Area. In this instance, an enemy can go toward the player, but must return to the grid once the target is no longer valid. It never goes further than the map’s LeashDistance from the grid (a map value, set very high to start so there is no safe spot just past it). As built (M29) a monster only chases where it can walk in a straight line over the grid, so it never leaves it yet and LeashDistance is not used
   * The grid only goes to the front of the camp. Once enemies reach the end of the grid nearest the camp, they can move freely towards camp targets and players
* Pathfinding (decided 2026-09-23, for performance): enemies never find their way one by one. The server keeps one flow field, a grid where every cell stores the way toward the Refinery, shared by every land enemy, so each enemy’s step is a single lookup
   * It covers the Wave Areas and the Camp Area, a Part under Camp.CampArea bounding the inside of the camp. Players can’t place anything in the camp, so the camp part of the field is worked out once when the run starts
   * The Wave Area part is recomputed only when a Tower, Trap, or Wall is placed, destroyed, or rebuilt
   * Walls, the gate, and placements count as passable at a heavy cost, so enemies take any open way round and attack what blocks them only when there is none. A gap narrower than MIN_PASSABLE_GAP_CELLS (2, GameData/Monsters/Behavior) between a wall or placement and another wall, blocked ground, or the zone's edge is closed to ground monsters (FlowField.markPinched, yellow in the path view), so a crew cannot funnel a night through a one-cell slot; a narrow place made by the map alone stays open (decided 2026-10-02). The walkability scan tests real collision shapes (GetPartsInPart), not bounding boxes, after a tilted butte's box swept over spawn 3 and froze a whole wave (2026-10-02)
   * A barrier costs more the thicker it is, cell by cell: the gate's box is three cells deep where a wall is one, so a blocked crowd breaks through a wall before the gate
   * Every monster walks its own lane, up to 12 studs to either side of the shared route (chosen at spawn, LANE_SPREAD_STUDS), so a crowd moves as a band rather than a line; the lane narrows wherever the ground does, as at the gate. A monster heads straight for the farthest point up to 8 cells along its route it can see (LOOKAHEAD_CELLS), so it walks smooth lines rather than cell to cell (decided 2026-09-23)
   * Monsters push apart from each other (SEPARATION_STUDS, 4). A monster attacking holds its ground, and one that makes no headway toward where it is going (a crowd stalled at a wall or round the Refinery) stands still rather than churning. One that has made no headway for JAMMED_REROUTE_SEC (1.5 s) moves its lane to the other side of the route and, for JAMMED_TARGET_IGNORE_SEC (3 s), follows the route instead of the target it could not get to, so a Bomber stuck behind a crowd of zombies at a wall walks round them rather than into their backs (decided 2026-09-24)
Creating Waves
* The goal of the wave creation system is to easily generate waves for different maps with minimal set up, as maps are a major content vector
* Every wave consists of groups of monsters that spawn at a specific spawn at a specific time
* There will be different numbers of groups in different waves
* Groups spawn at specific times, based on seconds from night start. If there are no active enemies (they have all been killed) while groups are still waiting, the next group spawns at once and every remaining group moves up by the same amount, keeping their spacing, so there is never any dead time (decided 2026-09-23)
* Once all groups are spawned and all enemies are destroyed, the wave/night ends
* Wave creation consists of a combination of hand authored waves or waves automatically generated at random based on a set of parameters
* Every wave is generated by a table with 2 entries:
   * Night: number correlating to night number, determines which night this wave spawns on (only one wave per night)
   * EnemyData: a list of groups, each with:
      * Enemies: one or more pairs of EnemyType (the specific enemy type) and NumberOfEnemies (the number of that enemy type that spawn in this group). A group can mix types
      * SpawnLocation: which spawn the group is spawned at in the map (number)
      * SpawnTime: measured in seconds from night start (0 is exactly at night start, 10 is 10 seconds after night start, etc.)
* Any night that does not have a data entry generates a wave based on map specific parameters (as built, M30: an authored night is played only on its own night, never replayed; the parameters are one GENERATOR table per difficulty in GameData/Waves/<Map>, and how the rule rolls, the share weights, the spawn window share and jitter, is GameData/Waves/Generation, the same on every map; a night that generates nothing, because nothing is unlocked or the map has no spawns, warns and ends when the field is clear)
   * Every enemy type is assigned a difficulty value
   * Every map has these parameters:
      * StartingDifficulty: the cumulative difficulty value for the starting wave
      * DifficultyIncreasePerWave: the difficulty value added each wave; GrowthPerWave: the share the target also grows by each wave (0.12 is 12%; decided 2026-09-24: a crew’s power compounds through its economy and upgrades, so a linear climb alone goes flat), 0 for a linear climb. The wave never reads the player’s defenses: scaling to them would make spending on defense pointless
      * WaveDifficultyRange: how close to the TargetWaveDifficulty the wave’s total must be to be a valid configuration (default 5)
      * MinGroupDifficulty and WaveSpawnLength (per map, not per difficulty; decided 2026-09-24): a wave makes one group for every MinGroupDifficulty it can pay, rounded down and never fewer than one, and every group is worth at least it, so the one number sets both how many groups a night has and how small the smallest can be; and how many seconds after night fall the last group spawns. MaxTimeBetweenGroups (per map): no two of a generated wave’s groups in a row are further apart than this, so a night of few groups bunches them rather than leaving a lull. Since 2026-10-01 both climb with the night (WaveRules.minGroupDifficultyFor / maxGapFor): the group bar rises MinGroupDifficultyPerNight (5) every night after the first, and the gap cap shrinks GroupGapShrinkSecPerNight (2) a night to a MinTimeBetweenGroups floor (8 s), because the ninth playtest showed a fixed bar only adds 80-point groups that die one at a time 25 s apart; now night 8 is one 230-point group and night 13 three groups of 180 landing 8 s apart. Deadman’s Canyon: 80, 90 seconds, and 30 seconds (2026-09-29; the group minimum doubled that morning so a small night arrives as one big group, and the window and cap grew after the eighth playtest, where two groups 10 seconds apart played as one wave and the Refinery fell on night 8; before that 40, 60 and 10)
      * AvailableEnemies
         * EnemyType: the specific enemy types available in this map
         * WaveUnlocked: the wave number in which this enemy can start to spawn
   * TargetWaveDifficulty = (StartingDifficulty + DifficultyIncreasePerWave * (WaveNumber - 1)) * (1 + GrowthPerWave) ^ (WaveNumber - 1), times the party’s wave multiplier. Deadman's Canyon Normal: 24, 12, and 10% (set from the balance sheet on 2026-09-28 after five playtests; the first pass was 10, 4, 12%, the first playtest tuned it to 18, 18, 12%), so nights 1 to 4 run 24, 40, 58, 80 and night 10 is 306. Hard 28, 26, 6% and Nightmare 30, 26, 6% are provisional until Normal is confirmed in play; each stays above the easier tier through that tier's target night, and Hard and Nightmare use Normal's unlock order shifted two and four nights earlier
   * Generating a wave (group rule decided 2026-09-23):
      * Group count: TargetWaveDifficulty / MinGroupDifficulty, rounded down, at least one (as built 2026-09-24). Early waves are one group, late waves many
      * Each group gets a share of the wave’s difficulty with a random weight (0.5 to 1.5), so some groups are big and some small
      * Each group is filled by drawing unlocked enemy types one at a time at random from those that still fit what is left of its share, until nothing fits (no one-kind rule; decided 2026-09-24). Cheap enemies come in numbers and strong ones in ones and twos, mixed as the draws fall, and a wave never overshoots with one huge enemy
      * Leftover difficulty rolls into the next group; at the end the total is topped up with random unlocked enemies that fit the shortfall, or trimmed, until it is within WaveDifficultyRange of TargetWaveDifficulty
      * Groups are spread across the night’s spawn window with a little random jitter, and the biggest group always spawns last so the night builds to a peak. Spawn locations are picked at random, never the same one twice in a row
      * The generator is pure data in and data out, so it is unit tested and any night on any map can be previewed without playing (the Monsters dev panel’s Preview wave prints a night’s roll to the Output for the run’s map, difficulty, and crew; Preview curve prints the target for nights 1 to 20 as a column, so a tuning change is read rather than worked out; the Run panel’s Set day makes the coming night any night)
Wave Spawn Locations
* Every map has a set of Spawn parts in the map, each Spawn is assigned a number
* When creating waves, each wave group is assigned a spawn location
* Every map has a SpawnRadius value
* Enemies spawn in random locations within the SpawnRadius of the SpawnLocation, so they don’t all spawn on top of each other but still feel like a group
Monsters
Monster Creation & Behavior
* Like wave data, monsters need to be set up in a way that is very easy to add new monsters, as this is another major content vector
* Every monster has a base set of stats that are shared across all monsters (GameData, one entry per monster):
   * Name: System name. Every monster has its own model in the GameAssets.Monsters folder with this name in capitals (ZOMBIE_1, BRUTE_2)
   * DisplayName: the name players see
   * DifficultyValue: used to generate random waves
   * HP: how much health the monster has at spawn
   * Damage: how much damage a hit from that monster causes
   * Speed: how fast the monster moves through the environment
   * TargetPriorities: a table containing each target type, ordered by priority (i.e. {“Players”, “Towers”, “Traps”})
      * If a type is missing from the table, that unit will not attack that target type
      * Refinery is the #1 target priority for all monsters, so does not need to be included in this table
      * A monster goes for the highest-priority target within its DetectionRange, walks to it, and attacks once it is within its AttackRange (decided 2026-09-23). It only walks to a target it can reach in a straight line over open ground, so nothing is chased through a wall A ground monster's step never ends on unwalkable ground: at a wall it stops at the face and attacks, and at anything else (a post's footprint, a rock) it slides along the edge on whichever axis is clear, since a step refused outright left a monster walking in place at a cell edge (2026-09-29).
   * TargetDamageTypes: a table containing each target type that monster’s attack can damage, used for monsters with an AttackRadius > 0
      * If empty, it only damages its target
   * AttackType: either Melee or Ranged
   * DetectionRange: how far the monster notices a target on its priority list (20 for every monster to start). It never notices less far than its AttackRange, so a long-range monster still fires from a distance (added 2026-09-23)
   * AttackRange: how far from a target they need to be to attack (renamed from AttackDistance, 2026-09-23)
   * AttackRadius: on attack, targets within the AttackRadius are damaged. A 0 value means only the target is damaged. For projectile units, attack radius is measured from the projectile, not the monster
   * AttackInterval: the seconds between attacks (added 2026-09-23; the default is 1.5 for a monster without one: Launcher 3, Flyers 2, Titans 2.5 to start)
   * DieOnAttack: true or false. If true, the monster is destroyed on its first attack
   * DamageOnDeath: true or false. If true and AttackRadius is above 0, it deals its attack damage in the AttackRadius when it is destroyed
   * TraversalType: land or air
      * If land, the monster walks on the ground and must traverse the map/defenses
      * If air, the monster still must stay within the wave area grid, but doesn’t need to worry about avoiding obstacles
         * If an air unit is also a projectile unit, it stops moving (but continues the walk animation between attacks) and fires the projectile
         * If an air unit is a melee unit, it flies down to the target and attacks, then returns to flying when it doesn’t have a target or is traveling to a new target outside of its attack range (not built yet: no air melee monster is in the roster)
   * FlightHeight: air units only. How high above the ground the monster flies, in studs (added 2026-09-23)
   * WalkAnimation: the assetId for the monster’s walk animation, played on loop while in a walk state
   * IdleAnimation: the assetId for the animation played while a ranged monster stands and fires. Every ranged monster has one (decided 2026-09-23)
   * AttackAnimation: the assetId for the monster’s attack animation, played whenever the monster attacks
   * DeathAnimation: the assetId for the monster’s death animation, played when it is killed
   * Projectile: only needed for projectile units. References a projectile model in ReplicatedStorage. The projectile is shot from the monster to the target, applying the damage value to the target on impact
* Tiers: a monster that comes in stronger versions is a separate entry per tier, named with the tier number (Zombie_1, Zombie_2, Zombie_3) and shown as “Zombie”, “Zombie II”, “Zombie III”. Each tier has its own model, so a tier can look and be sized differently
* Many monsters are generated based solely on this data, though some more complex monsters may require specific behavior listed outside of these parameters
* These monsters are then referenced by the wave creation system
* There are currently 5 target types:
   * Players
   * Towers
   * Traps
   * Walls (all camp walls + gate)
   * Refinery (all units attack this by default)
* All units by default walk toward the refinery, and attack targets they encounter on the way
* If land units are blocked from progression toward the refinery by defenses or walls (i.e. there is no available path to the refinery), they attack the defenses/walls in the way
* A monster's hit on a player goes through the revive system (M32, "Health and Revives"): health only ever goes down, a just-revived player cannot be hurt for a few seconds, and at zero the player dies. Dead players are no target
* Models (decided 2026-09-23): a monster's look and size are set on its model in Studio, never in data. Each model is a Humanoid-free R6 rig with an AnimationController (scripts/studio/build_monster_templates.luau turns a rig into one; seed_monster_templates.luau gives a new monster kind a starting copy) and an invisible Proxy part: the monster's hit box, the single block it is drawn as far away, and, by its bottom edge, where its feet stand. Scaling a model scales its Proxy with it. Anything added to a model (a bomb, wings) is welded to the Torso so it moves with the body; the game turns off collision and queries on every part. Placeholder art: every monster starts as the same R6 rig with Roblox’s default animations, sized per monster
Monster Performance
* Many monsters on screen at once must run well on low end devices, and monsters are visible at all times, never popping in when streamed (decided 2026-09-23). Built to hold 300 at once and stress tested to 500
* Monsters exist only as data on the server, never as models. Their positions reach every player as a small packed update about 10 times a second, so no monster is ever streamed in or out
* Each player’s game draws the monsters itself from GameAssets.Monsters, with no Humanoid, moving them all together. Near monsters are fully animated; every other monster is drawn as its Held body, the whole rig baked into one part, so it keeps its own shape at any distance (the template’s Proxy block only stands in until a new monster has been baked; decided 2026-09-24)
* The update rate is by distance from each player (GameData/Monsters/Behavior): a moving monster within 80 studs every tenth of a second, within 200 studs every fifth, and anything further, or standing still, every 0.4 seconds. Each monster is drawn a moment behind the newest update and blended between updates, so movement stays smooth
* Measured in Studio (M29, a desktop PC): 300 monsters take about 2.6 ms of the server's time per update (10 a second) and 8 to 18 KB/s per player at the busiest, with the client at 60 fps; 500 take about 2.2 to 3 ms and 19 KB/s. Still to check on a phone
* The nearest monsters are animated (40 on desktop, 12 on touch devices or at a low saved graphics quality; DRAW_BUDGETS) and only monsters within the held distance (250 studs, 120 on the low budget) can be; everything else is the template’s Held body, its whole rig baked into one part so a crowd of hundreds is hundreds of parts rather than thousands, drawn at every distance and placed every other frame when far (decided 2026-09-24)
* Admins have a stress test dev tool that spawns any number of monsters and shows server step time, network use, and frame time
Monster Health Bars
* One health bar at a time (decided 2026-09-23): over the damaged monster under the reticle (the centre of the screen), showing its name and its HP; a monster at full health never shows one. It stays half a second after the reticle moves off, so sweeping across a crowd does not flicker, and it shows at any distance. A monster behind a wall is never picked, except from a post (decided 2026-09-30): a mounted gunner's reticle reads through the fortifications like their bullets do, picks a monster at any HP, and draws its bar on top of everything with one white outline (a single always-on-top Highlight moved between monsters, so it costs nothing to speak of) so a target hidden by the wall line can still be found and led. It is the same StructureHp bar the walls use, without the repair price
Monster Types
* The goal is to add a bunch of different monster types over time, but here is the first set of monsters with their data
Zombie
* Basic unit, simply walks and attacks. Meant to spawn in large numbers
* Data:
   * Name: Zombie_1

Seam
* The face in the rock (M68, designed 2026-10-26; revised the same day: the damage is the break, not the swing): a block of the deep mine with a face on every side (the designer’s SEAM model). It never attacks. Any swing breaks it in one hit whatever the pick, and the break is the trap: the block bursts into smoke that does half of a player’s base health and gives a long shove to everyone standing in it, so the player who swings at it point blank takes it and the second mistake kills. It cannot be shot; weapons pass through it. Breaking it from a distance, dynamite above all, is the safe way, which gives the Demolitionist a job in the deep mine and makes a stick worth carrying; a careful miner digs round it instead
* It never moves and never grows (the drift and the spread of the first design were both cut on 2026-10-26: a face that stepped to a new block, or grew onto the next, read as a bug in a game about looking at what you swing at). A Seam is the one block it woke in until it is burst. It spreads onto stone only, never onto ore, so a vein is blocked, never eaten. The lesson is “look at what you are swinging at”, which no other monster teaches, and the Prospector’s fast swing becomes a liability deep down
* Common (designer, 2026-10-26): 50 on Deadman’s Canyon from zone 2 down, the first iron band (20 from zone 3 for the first play the same day), each asleep inside one buried stone block drawn from the mine’s seed (GameData/Monsters/Seams COUNT, MIN_ZONE_INDEX; never beside a pocket, so a room’s wall stays the spiders’ discovery, and never two on neighbouring blocks). It sleeps unseen until a block beside it is cleared and one of its faces meets the air; then it wakes where the player is digging, which is the point: the face appears on the block in front of the pick, and the next swing is the one that counts. Neither the Ore Scanner nor the Geiger shows one, awake or asleep: eyes only. It hunts nothing and never leaves the rock, so it never counts toward a wave and the Camp Map does not draw it. Built 2026-10-26 (M68): a Seam is a set of grid cells held in Lua on the server (SeamManager, pure SeamRules), never a body, so no weapon can touch it; the awake blocks travel to every client as one short list and each client stands the designer’s SEAM block model (GameAssets/Monsters/SEAM: a 4x4x4 Rock with eyes and a mouth on every side, the primary part Rock mapping onto the block) on each of them, a hair larger than the block so it covers the rock, with no collision or query so the swing still lands on the rock beneath; a swing at one is taken by MiningManager’s interceptor and breaks the block outright whatever the pick; every broken block of an awake Seam, by a swing or by dynamite, bursts: the server hurts every player within the burst radius with the Seam named as the attacker, and each client plays the block out and shoves its own player if they stood in it; a Seam with no blocks is gone. Sleeping Seams never travel to a client. Dev panel: spawn an awake Seam on the nearest stone, wake every sleeping Seam, break the nearest awake Seam as dynamite would, and Show Seam locations, which hangs a purple SEAM billboard over every sleeping Seam’s block (the spider billboard with its own text; a marker goes when its Seam wakes, and the toggle survives a new run)

Drag
* The chase (M68, designed 2026-10-26; the name is a placeholder): the mine monster you cannot kill and must outrun. One sleeps sealed in a pocket of each of zones 3, 4, and 5 (three drawn from zone 4 down for the first play, 2026-10-26). Opening its pocket wakes it, and from then on it hunts whoever woke it, relentlessly, through the open air of the mine, drawn as a flat image with effects. Inside the mine it cannot be hurt at all; weapons pass through it. Touch is death. Its speed is its victim’s own walk speed less 5 (never under the roster’s 15; 3 for an hour), so boots never make it harmless and a flat sprint barely holds and every one-block step up, every dead end, and every stop to swing costs ground. Dynamite staggers it for a few seconds, the one thing that buys distance (the Demolitionist’s role in the escape); torches and the jet pack do nothing to it, though the jet pack climbs faster than it follows
* The only way to end it is to lead it out: the moment it crosses the mine’s mouth into the open it burns away, day or night (designer, 2026-10-26: it dies outside whatever the hour; a night version that the camp’s guns had to kill was dropped as confusing). So a discovery deep in the mine becomes a chase up and out, with the sun or the night sky the finish line. It never gives up a chase inside the mine, and the moment its victim is outside the mine it fades where it is, whether or not it reached the mouth (2026-10-26: it had hung at the entrance while the player stood just outside). If its victim dies it returns to its pocket and sleeps again at once, fading where it stood (from the death itself, since a solo death pauses the run and would otherwise leave it standing over the body; 2026-10-26), so a solo player’s grave is not a permanent haunting and a crewmate can still mine the zone; a crewmate waking a second one while the first is loose is the risk of mining deep together
* It follows the open air of the mine cell to cell, floating, no gravity, so any tunnel a player can walk it can follow. It keeps its victim’s recent trail (the cells they passed through) and follows that when it loses sight of them, so hiding round a corner does not work; only distance does
* Built 2026-10-26 (M68): a MonsterManager crawler (so it never counts toward a night, is never pushed apart, and dies to no forced dawn) stepped by DragManager through the monster manager’s per-kind stepper, with pure DragRules: a breadth-first search over air cells capped per step (GameData/Monsters/Drags SEARCH_MAX_CELLS), the victim’s trail sampled every quarter second and read newest first when the search cannot reach them, a straight line at a victim who has left the grid (which is how a chase ends at the mouth), and a slow drift toward the last known cell when nothing else applies. Its Damageable takes damage at zero, so every weapon and tower already passes through it; the touch is its melee (100). A woken Drag hangs in its room for WAKE_DELAY_SEC (1.5 s, the shriek) before the chase starts, the digger’s one moment to turn and run (with no delay a wake killed them before their next step). Its pockets are picked from the deep zones among those the spiders do not hold. Drawn from GameAssets/Monsters/DRAG, which turns to face the camera every frame (MonsterRules.visualFor isFloater): the designer’s rig (2026-10-26), an R15 character in the company Hard Hat with its face texture cleared, red Neon eyes welded to the head, and a smoke emitter on its root, built by build_drag_template.luau from the Workspace Rig (no Humanoid, an Animator, the Proxy, feet at the pivot); a flat plate was the placeholder for an hour. Dev panel: Spawn Drag ahead (hunting the tester, seated along their look), Show Drag pockets (the spider billboard relabelled DRAG in blue). Played 2026-10-26: woken, the kill on a standing player, and the chase down the corridor ending in its death at the mouth

Adjusting for Different Player Counts
* The crew size that scales a run (GDD "Maps": Party scaling) is a single number the gameplay server samples, never the live player count: once at run start (the party that boarded), again at every dawn (M28, decided 2026-09-22), and whenever a crew member leaves the run (2026-09-25); it only ever goes down. On a departure the uranium target drops at once and the radio re-checks it, and the next night is built for who is left; a night already under way keeps its wave
* It only ever goes down. A player leaving eases the run at the next dawn; a player joining late never makes it harder
* Everything that scales by crew reads this one number: ore yield per break, the uranium rescue target, the wave difficulty (the generator’s target, or an authored wave’s counts) and enemy HP (M30)
* The day-start message states it plainly, for example "Day 3. Crew of 4. Ore 1.45x, Uranium target 1.15x", so the multipliers are never a surprise
Health and Revives
* Built 2026-10-05 (M32), replacing the earlier notes under this heading (a 30 second countdown and a free solo revive are dropped). Tuning is GameData/Run/Revives
* Players have a static health of 100 (GameData). Damage comes from monsters only (no friendly fire, no fall damage). Every hit the player takes, whatever did it, plays the PlayerHurt sound to them alone and fades a red edge vignette in over 0.5 s and out over 0.5 s (HurtVignette, the Stim glow's shape in red; 2026-10-26, M68), read from the health the server lowers so no message is needed. There is no healing in a run (decided 2026-10-05): no Med Kits, no way to heal yourself or another player, and Roblox's own slow regeneration is switched off for every character. Med Kits were considered (a carry cap and a Gold price that rises with each one a player buys, since any flat price turns trivial as Gold grows) and set aside
* If health reaches zero, the player dies. The character is never destroyed or respawned (Roblox's Reset Character is switched off): its body drops limp where it fell for the Game Over screen, then it is moved to the DeathRoom (one closed room far above every camp, once in the gameplay place) and held still there until revived
* The Game Over screen (designer's sequence, 2026-10-05): the world turns red (a ColorCorrection on the camera: brightness 0.2, contrast 0, saturation 0, tint 255, 0, 4), the GameOver sound plays, the GameOver gui reads "YOU DIED", the HUD is hidden, and the camera circles the fallen body from above for 6 seconds; the screen fades to black over 2 seconds and the Game Over music starts; the black holds for 3 seconds, during which the character is moved away and the camera goes to the player's grave; the Results Menu opens under the black, which fades away over 3 seconds. The revive windows below count from the moment the menu is on screen, so the screen costs the player none of them
* When they die, a grave is laid in the camp's Cemetery for them: the designer's Grave template (GameAssets.Grave) on the lowest free of the six numbered plots (Camp.Cemetery.Plots, each the size of the grave's Ground), with the player's display name, their avatar's face, and "DAY N" on the stone. A player who leaves a run under way leaves a grave too (their own, if they were already dead), which stays until the run is over. A revived player appears on their own grave at full health and cannot be hurt for 5 seconds; their grave is removed. A dead player keeps everything (backpack ore, tools, their claimed post). The Cemetery is a required part of every map (GameplayMapManager checks it)
* After dying, a player sees the Results Menu on the left of the screen beside their grave (the Grave template's CameraLocation marker is where the camera stands), listing their stats, with a Revive button and a Spectate button (the Spectate button only while someone is alive to watch)
   * The Revive button reads "REVIVE" with the Robux price (read live from Roblox), or "FREE" when a saved credit will pay. Pressing it opens the purchase; if successful the player is revived at once
   * Players have 60 seconds to buy their own Revive, in Spectate Mode too; after that the button is gone for that death. They can buy unlimited revives
   * A solo player is only ever offered their own Revive (decided 2026-10-05): it brings them back where the run stands, with no day started over, as often as they buy it. The run is held still for the 60 seconds and lost if they run out
* Alive players can also buy a revive for a dead player by walking up to their grave in the Cemetery, where a proximity prompt reads "Bring [DisplayName] back from the dead". Triggering it starts the Friend Revive purchase (a dev product). The prompt exists only while the dead player is still in the game; a Friend Revive has no time limit. The player being revived gets "[DisplayName] revived you." and the buyer "You revived [DisplayName]"
* A revive purchase is never refused (decided 2026-10-05, forced by how Roblox purchases work): by the time the server hears of a purchase the Robux is already spent, and Roblox's refund of a refused purchase is unreliable. If the player a Friend Revive was for has left or already been revived, or a Revive or Team Revive can no longer apply (the run is over, two players bought the Team Revive at once), the buyer keeps a saved revive credit of that kind in their save, and their next one of that kind is free ("FREE" on the button, no prompt). A credit can only ever come from a purchase. Every receipt's purchase id is saved so a receipt Roblox sends again is never granted twice (PurchaseManager, shared with M40)
* Team Revive (decided 2026-10-05): when every player of a crew of two or more is dead and the Refinery still stands, the run freezes (the clock, the monsters, and the wave hold where they are, as the Pause dev tool does, though the PAUSED word shows only for the dev tool since 2026-10-09) for 60 seconds, and every dead player's Results Menu offers the Team Revive in place of the Revive button, reading "REVIVE CREW AND RESTART THE DAY" with the Robux cost. One purchase revives every player still in the game and restarts the current day: the monsters are removed, the groups still to spawn are cancelled, a rescue under way is called off, and the same day number begins again from dawn, so the same night comes a second time. The run is lost only if the 60 seconds end with nobody revived. A crewmate leaving can wipe the crew too; that gives the same 60 seconds
   * Once per run. A replayed day is an extra day of mining, so the limit is what keeps it from being farmed
   * Nothing is rewound and nothing is repaired: the mine, the balances, and the upgrades stay as they are, fallen walls stay rubble, and the Refinery keeps the HP it had left. The crew has the day and their Iron to rebuild and plan differently
   * It never skips a night, so it cannot buy a win. On the rescue wave the day restarts the same way and the crew calls the helicopter again when ready
   * A wipe during the day restarts that day the same way
   * Once the Team Revive has been used, a later wipe freezes the run the same way and offers each player their own Revive
* The Refinery is never revived or restored for Robux: that would be selling the win
* While a player is dead the HUD is hidden (it is no use to them and sits over the Spectate bar), so are a phone's thumbstick and jump button, and on the Game Over screen and the Results Menu so are the wall HP bars that draw through the world and every notification. All of it comes back on revive; the bars and the notifications come back in Spectate Mode as well
* Developer products (created 2026-10-05): Revive 3716709853, Friend Revive 3716709889, Team Revive 3716709964. A dev tool revives without paying, for testing; Studio test purchases exercise the real flow
Spectate Mode
* Built 2026-10-05 (M32). A dead player who presses "Spectate" on the Results Menu watches a living player
* The view is Roblox's follow camera on the watched player's character (the first-person lock is lifted for it): drag to orbit, scroll to zoom. The world, the mine, and the monsters stream round the watched player
* The Spectate bar at the bottom centre: a left arrow, a box naming the player being watched, a right arrow, and above the box, centred, Results (reopens the Results Menu) and Return to Lobby (teleports the player to the lobby). To the right of the right arrow, centred between it and the edge of the screen, the Revive on offer with the seconds left counting down above it; it goes away when the time is up
* When the watched player dies or leaves, the view moves to the next living player. When nobody is left alive, spectating ends: the camera holds where it is (never on the DeathRoom) until the grave view takes over, and the Results Menu opens with no Spectate button
Results Menu
* Built 2026-10-05. At death or at the end of a run, players get the results screen. It shows, one row each with the resource icon after the words:
   * Uranium refined (the uranium this player carried to the Refinery themselves)
   * Diamonds earned
   * Gold refined
   * Iron refined
   * Enemies killed
   * Damage given
* Nights survived is not a row: it is written on the player's grave
* Group Rank: when more than one player has been in the run (even if the others have since left), a column under a "GROUP RANK" header shows the player's place in the crew for each row ("1st", "2nd"; equal numbers share a place). A solo player sees no column and the numbers sit at the right edge
* Kills and damage by a player's Towers and Traps count toward that player's Enemies Killed and Damage Given (decided 2026-10-05)
* After death, there is a Revive button (the offer and its price) and a Spectate button; with neither Spectate nor Return to Lobby showing, the rows and the Revive button grow into the empty space
* At the end of a run (won or lost) the same menu reads "RUN WON" or "RUN LOST" with a Return to Lobby button, which teleports the player to the lobby (the summary and rewards are M33)
* The Game Over music loops under the menu and fades out, stops, and rewinds when the player goes to Spectate Mode, presses Return to Lobby, or is revived
Classes
* Status (decided 2026-10-15, replacing the Characters design of 2026-10-05 and the Class system of 2026-10-03): the lobby economy is Classes. The twelve launch classes below are designed and locked one by one on 2026-10-15; nothing is built. The order of work is to build a set of classes that feel good first, learn what a class costs to make, and only then decide how classes are unlocked and progressed (the candidates are parked at the end of this section). The reasoning for classes over the reroll gacha: a gear reroll needs more content than the game has, discourages a built player from trying new content, and is a paid random item that several regions restrict; consumable loot boxes are the same plus pay-to-win friction in a shared defense; sold permanent power makes a growing curve every Contract tier must be rebalanced against. The Character Select Menu and Character Sheet as built (M37, M55) carry over: a card is a class, the gear cards show the fixed kit with no reroll, the skill rows keep theirs, and CharacterManager becomes the owner of class instances
* Requirement one: every class can play a full run alone, some with a much harder time. So every class has a post and a handheld weapon for the night and mines with the pick axe and the Mining Supplies Store by day like everyone; a debuff never touches survival (HP, revives, wall repair) and the solo run on Normal is the playtest every class must pass
* A class is four items, three skill slots, one buff, and one debuff:
   * A handheld weapon, shared (the Pistol for the classes whose night is the weak half, the Rifle for the rest), except where the weapon is the fantasy: the Ranger and the Pyro carry their own (the Sniper carried a Sniper Rifle until 2026-10-19; the Railgun is the Sniper's gun, so the Sniper carries the Pistol and the Sniper Rifle stays in the weapon table unused). No hand weapon lands headshots (decided 2026-10-19; they were every hitscan weapon's for an afternoon): the headshot is the Railgun's alone. A gun's first-person hold can be moved per template (a ViewModelOffset the designer sets on the held model; the Assault Rifle sits half a stud back)
   * A Post Weapon, unique to the class (see "Post Types"); the Recruit's Machine Gun is the one post nobody buys
   * One Tower, from the shared pool; several are carried by one class only in practice (Mortar, Drill Rig, Rock Slide, Repair Tower, Tesla Coil)
   * One Gadget, unique to the class: a class-only tool in the tool bar (the GADGET slot, pictured and captioned for the gadget, M66), the crew gift that a crewmate would ask the class to bring. Posts and gadgets are the two slots worth bespoke art, since they are where a class is felt all night. A gadget that fights scales with the nights through one Tower-like level bought at the Post & Gadget Upgrades table (M67, see "Upgrading a Post Weapon"); a utility gadget stays fixed
   * Three skill slots that work as built: unlocked through progress, a free roll on unlock, Diamonds reroll (how slots open is part of the parked progression decision)
   * A buff and a debuff as entries in a modifier table (mining speed, handheld damage, post damage, defense cost, mining upgrade cost, repair speed, backpack capacity, move speed, ore yield and so on, every class setting a few from a default of 1.0, in GameData, applied in the one place each stat is computed). One of them is a core stat every class states outright, 1.0 included, so it reads on every row: move speed (mining strength was the second from 2026-10-19 until 2026-10-22, when every class came to swing alike and the mining identity moved into prices and the Prospector's swing speed). The debuff is the swing pace (decided 2026-10-23; a price dial on mining upgrades and defenses was the model for the day before and was dropped as confusing, so every stand and table charges its catalogue price for every class): a class's mining speed scales the pick's swing interval, the server's hit cooldown, and the swing animation together, so it is felt on every block at every tier. The rule that sets it is the class's combat output against the Recruit's Machine Gun and Pistol on one body at tier 0, about 2% of pace per 10% of combat for a generalist and a discount for a specialist that is only strong in its lane: Ranger 0.7 (152%), Gunner 0.75 (142%), Air Defense 0.8 (125% on one body, far more on flyers), Sniper 0.85 (97% on one body, 150% down a line), Pyro 0.9 (56% on one body, 140% on a group), the Recruit 1.0, the Demolitionist 1.1, the Prospector 1.2. A mining power dial was the debuff for a week before and was dropped: the pick and the rock triple together, so a fifth more or less damage changed no swing count. Health was tried as a third the same day and dropped as one variable too many; every class has the same health. A buff is a modifier on something shared, never a tuning number on the class's own kit; the debuff comes from the group the class has no role in, so a day class pays in combat or building and a night class in mining
* Roles: a class is a primary role from one group and a secondary from another, the unique post expressing the primary. Combat (Balanced, Tank Destroyer, Group Destroyer, Air Defender, Foot Soldier), Building (Tower, Trap, Repair), Mining (Balanced, Clearing, Finding, Hauling), Support. Trap and Finding live as secondaries or skills, never a class of their own, since traps are level content everyone builds and finding is a gadget

Boosts
* Decided 2026-10-15: Boosts are the game's consumables, the recurring spend, and the one place power is sold, because a Boost's effect ends with the run and so never moves the balance. Each run a player brings up to two Boosts, picked on the class sheet beside the loadout; a Boost is spent when the run starts. Boosts belong to the account, not the class
* Where they come from: run-end drops (set so a free player has one Boost most runs and two sometimes, the store being the top-up and never the only source) and the Store Menu for Diamonds, with Robux bundles. Always sold by name, never from a random box, so a Boost is never a paid random item; the free drop is the random one
* Launch Boosts:
   * Supply Crate: a Tower of the player's choice (from their loadout) stands pre-built at the gate on day 1. The crew sees it, the buyer feels it
   * Dynamite Kit: 5 dynamite in the backpack at the start. Since dynamite became the Demolitionist's exclusive (2026-10-15) this Boost is either Demolitionist-only or replaced; to be decided with the Boosts prices
   * Spare Parts: the walls start the run at fortification tier 2. Crew-wide, nobody resents it
   * Field Medkit: one free self-revive this run (the revive the game already sells, brought in rather than bought dead; see "Health and Revives")
   * Gold Voucher: 30 Gold Bars at the start. The cheapest, the one bought every run
   * Extra Diamonds Tap: night milestones pay 50% more this run. The booster, Robux only
* Rules: a Boost helps the crew or the buyer's own run and never hurts anyone else's (in co-op a consumable that works against other players is where the feel-bad lives, and there is none here). Contract tiers are tuned to no Boosts, so a Boost makes a tier easier, which is what a consumable is for, and the top tiers stay honest because the effect is bounded and chosen. A spent Boost is logged in the run record beside the dev commands, so runs with Boosts are never averaged with runs without

Technical Overview
Product/Marketing targets
This game should play well on phones with pretty low bandwidth and even only 2GB of RAM. The biggest limitation will probably be bandwidth if we do things the naive roblox way, so keep this in mind (and see ‘shadow’ system below). 
Reference Games/Code
Review the code in ~/md (md stands for ‘merge dragons’, though the game ended up being called ‘fuse dragons’, sometimes referenced as ‘dragons’), and ~/square (‘lucky squares’, ended up being called ‘lucky lights’, or just ‘lights’). Dragons was written almost entirely by hand and code quality and structure is considered quite good. Lights was entirely written with AI, and while the structure is good, the code has largely not been reviewed.


There are many systems or structures we should reuse from these games. Lights is newer than dragons, and hence tends to be more advanced and have better/deeper abstractions. Systems we should definitely copy–the player state loading/saving system, which uses a 3rd party library (code in both projects) for user profiles that handles errors incredibly well; the loading/ready system for players in Lights is excellent. Using Iris library for dev tools, and locking dev tool access to the members of a group, is also a great setup we should use here too. Lights has a sophisticated system to capture screenshots and turn them into image assets in Roblox Studio that we likely want to copy.


Both games separate out most “dials” or otherwise configurable numbers controlling game play into data-only scripts in the ServerScripts/GameData folder. Let’s do the same here. Difference–in the other games, that folder was NOT checked into git, and editing the files in studio was authoritative. In this game, let’s check them into git.


Both games also have an object/item system which works well, but is a bit less applicable here where less is persistent between sessions. Analyze and make suggestions on this.


Copy and use coding standards from those games to start. Don’t use abbreviations in variable names, use luau type system a lot (but the LSP is not great, so don’t overindex here–we want to use colon functions for object ‘method’ functions for example, and the LSP doesn’t handle it well). Setup a test suite you can run from Studio for all core, testable units, same as Lights.


Look to Lights for some key decisions–all messages go over one ‘RemoteEvent’ (and are then dispatched by name) to be able to detect missing handlers. Almost all game data setup is sent from the server to the client in a spot in the PlayerGui, which allows client-inspection of all of a client’s state by a human to be trivial, which helps us quickly debug problems.


Key thing about Roblox development–we don’t want to use parts/models/meshes in the data model on the server very much, because they get replicated to clients at very high fidelity, and very high cost, giving us very little control. Look at the ‘shadow’ system used in both games–we place an invisible part on the server, clients get it (or not) depending on streaming, and then we set attributes on that part on the server, that the clients read and then render changes, animations, etc. This game is a bit different from our reference games, so there will be differences here, but while we must validate all significant game play actions on the server, we should be doing that by keeping game state in the server’s lua data structures, mostly NOT in parts in the workspace (except for shadows).


In particular, mining needs to be carefully planned and thought through–the server probably should NOT store every minable thing as parts, but instead as a lua data structure that gets shared with the clients, with messages sent back and forth with updates to that data structure.
Decisions/Project Philosophy
We are designing this game to be commercially successful. We want a good amount of consistency–let’s decide font choices for UI and standards for centering, capitalization, when to use exclamation points (very rarely), etc. and then stick with them across the project. When copying in big parts of UI from our reference games (especially the premium shop, inventory, index, playtime rewards, daily rewards, etc.), always adjust the UI to our standards, even if the functionality remains the same or at least similar.


We want to relatively quickly build up the core game play, even if the polish and graphic fidelity doesn’t exist (we can play the game where every attacker is just a cube just fine), and then add artwork and polish and sound effects etc. later.


Our first step is to take this document and have you turn it into a set of phases of development. Phase 1 is probably “get studio, rojo, etc. setup and the places able to be run”, phase 2 is probably “setup player joining/leaving and lobbies”, phase 3 might be mining, phase 4 might be full game play. There should probably be about 8-10 total phases, each with 3-10 milestones each representing one or a small set of features that we will be building in sequence. Don’t ever commit code or mark a milestone complete without explicit approval. As we setup this project and you’re copying lots of standards and memories and instructions from the reference projects, please ask us if you think anything is contradictory or if you think something is a bad idea or wouldn’t apply, or if you just don’t know if we want it in this project. Once we build a few milestones together, you’ll be able to make a lot of progress with a lot less feedback while still staying aligned to the goals of this project.
